# Fluent 2 验收方法

设计判据见[设计参考](design-criteria.md)；运行场景、环境记录和证据能力以[现有 WinUI 验证矩阵](../../momoka-verification/references/winui-validation.md)为准。本文件说明如何选择和判读，不增加交付闸门、全量组合或真实服务器操作权限。

## 按变更选择

1. 列出受影响的页面、控件、弹层及状态；如果改共享样式或模板，搜索实际使用者，挑选能覆盖不同内容密度与输入方式的代表入口。不要只检查改动文件，也不要因此扩大到全应用改造。
2. 从设计参考挑选判据，并按项目当前交付级别选择静态检查、行为测试与运行检查。文字/间距修复一般不触发新交互的 Gallery 流程；新模板、控件和交互按 Shell 技能及 CLAUDE 的触发条件执行。
3. 需要视觉取证时先看正常界面的截图，记录实际尺寸、主题和状态；交互结论另用操作或 UIA 核对。没有运行画面只能做静态审查，不能宣称界面整体合格。

| 改动维度 | 选择的判据与检查重点 |
| --- | --- |
| 布局、间距、文字 | 分组和主操作明确、同级对齐；相关宽窄窗、长文本和文字缩放下不遮挡核心内容 |
| 颜色、主题、图标 | 语义角色和信息含义稳定；核对实际前景/背景对比度、状态辨识及相关高对比度表现 |
| 圆角、描边、层次 | 根据控件/容器角色判读；相关嵌套、裁切和窗口状态下没有露底或重叠 |
| 材质、透明度 | 按项目允许的表面及材质方法检查；分开记录系统效果、实心回退和实际画面 |
| 控件、模板、弹层、导航 | 操作语义、输入、焦点顺序和返回目标正确；实际状态与 UIA 名称/角色/值相符 |
| 加载、空态、错误、能力恢复 | 反馈区分原因、下一步可达、命令实际受保护；状态恢复不丢已有选择和偏好 |
| 动效 | 过渡表达明确；中断、反向及关闭动效后状态与输入仍正确 |

表中各项仅在受影响时选择。主题覆盖、DPI、读屏、触摸等具体场景从现有矩阵和当前交付要求取并集，不另建固定的全部笛卡尔积。

## 证据与结论

- **静态证据**：当前文件、资源键、绑定、框架/样例版本及测试断言。能证明接线或规则，不证明最终像素、真实焦点和读屏体验。
- **画面证据**：截图位置、窗口/缩放/主题、触发状态。能证明该配置的可见结果，不证明弹层关闭语义或其他配置。系统材质不能只凭 XAML 离屏截图下结论。
- **交互证据**：实际步骤、输入、观察到的焦点/选择/命令结果或 UIA。自动化树可见不等于 Narrator 朗读已验证。
- **测量证据**：实际对比度取值、目标边界或性能数据及采样条件。不要凭“看着清楚”“感觉顺滑”宣称数值过线或性能改善。

每个结论选用以下状态并说明范围：

| 状态 | 使用条件 |
| --- | --- |
| 通过 | 本次适用判据已有足够证据满足；注明配置和范围 |
| 失败 | 存在违反判据的可复现现象，列位置、触发条件与用户影响 |
| 未验证 | 所需画面、交互、环境或数据缺失；列补验入口，不推定通过 |
| 不适用 | 说明该判据与本次表面/状态无关的具体原因 |
| 已确认项目例外 | 引用 CLAUDE 中适用取舍，记录与官方建议的差异；仍检查不受例外豁免的可读性与交互 |

执行时的失败、跳过、未执行等原始结果按验证技能保留；上表不用于把跳过的必需检查改名为通过。发现官方建议与项目取舍冲突时，按 CLAUDE 的确认规则处理，不能仅凭本技能取消既定例外或认可新偏离。

## 交付记录

按任务大小使用简短列表或表格，保留以下内容即可：

| 字段 | 填写内容 |
| --- | --- |
| 对象与状态 | 页面/控件、触发步骤、数据与输入、主题/尺寸等相关条件 |
| 判据与依据 | 具体可观察预期；官方页面、项目规则或资源位置 |
| 实际结果 | 实际看到或测到的行为；不能用预期行为复述代替 |
| 证据与状态 | 当前测试/截图/UIA/测量的定位及通过、失败、未验证等结论 |
| 后续 | 必要修复、补验入口或已确认例外；没有后续时省略 |

审查报告先说用户影响最大的发现，随后给依据和建议；没有发现时仍说明检查范围和未验证项。严重程度取决于任务是否被阻断、信息是否不可读或操作是否误导，不仅取决于与参考图相差多少像素。

纯技能或文档改动的结构、链接和格式检查只验收技能文件本身；没有执行产品运行检查时，不写“Fluent 全面达标”。
