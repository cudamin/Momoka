# Visibility, dialogs and measured XAML pitfalls

Read only for the affected code path. Policy is in [CLAUDE.md](../../../../CLAUDE.md); these are implementation notes and historical evidence, not extra approval rules. Recheck named owners in the current tree.

## Capability-dependent visibility

The search-page source selector is a user-requested exception: all four source tabs stay visible after search, disconnection and AniBT disablement. The selected source stays unchanged; unavailable sources show a recovery explanation and reject query execution. Other dependent actions retain the normal hiding policy.

Apply [CLAUDE.md's visibility policy](../../../../CLAUDE.md#功能可用性与显隐). Establish the prerequisite and the scope of each control before editing XAML: a persistent preference for a supported playback mode is not inapplicable merely because nothing is playing. Use confirmed service capabilities for service-backed actions; a saved enable flag alone need not mean that the service is usable.

- Trace every dependent surface: settings rows, hand-written cards, navigation, context menus and already-open child views. Collapse the whole inapplicable row or group, including its note and spacing; retain other usable content and the switch or selector that restores the prerequisite. `IsEnabled=false` alone does not meet the policy.
- Reuse the existing notification or rebuild path. `SettingsViewModel.ScreenshotCard` constructs the applicable rows, and the format/lossless controls call `RefreshScreenshotCard` through their `after` callbacks. The callback replaces the affected section and refreshes the selected category; hiding rows does not erase their stored values. For bound visibility, notify every dependency and reevaluate on `Attach`, import and reset. Keep bound collection instances stable.
- MoviePilot uses `MoviePilotService.Available` and `AvailabilityChanged`; `ShellPage.MoviePilot.cs` also closes dependent views and prunes unusable navigation history. Follow [momoka-moviepilot](../../momoka-moviepilot/SKILL.md#可用性与入口显隐) for that lifecycle instead of checking only `Enabled` at first load.
- 「更多」菜单的下载、删除、字幕、编辑/识别/刷新/扫库入口按服务器账号策略收起：`ServerCapabilities.ProbeAsync` 按在线来源读一次用户策略，菜单通过 `IShellActions.MenuPermissionsFor(scope)` → `ItemMenuPermissions` 判断。只有明确答 `false` 才隐藏，`null`（旧服务器、探测失败或尚未返回）照旧显示，由服务器拒绝；`ItemMenu.For` 的默认参数就是全未知。
- **MoviePilot 的两趟探测（连接、媒体管理能力）可能在「更多」已经开着时才回来。** 按菜单上的 MP 行集合比较（不是按能力布尔值）：能力增加就原地重排补行、菜单不收起，AniBT 识别的 genre 补查也要跟着补跑；只有 MP 入口要失去（掉线、失权）才收起整张菜单。一张本来没有 MP 行的菜单（演员卡）和服务器权限迟到收起的那几条都不该连累整张菜单。2026-10-30 用户报「刚打开应用时少几条、过几秒菜单自己关闭、再开才有」；`MoviePilotMenuFillAsync` 探针覆盖先后顺序和真掉线收起。
- Keep visibility separate from execution guards and effective option application. An old menu or asynchronous callback must still be rejected after its prerequisite changes. A hidden preference may still need an explicit reset or a complete option push to prevent stale backend state; follow the owning domain skill.

Use [momoka-verification](../../momoka-verification/SKILL.md#capability-dependent-visibility) for initial, hidden and restored states, real layout and keyboard checks. A property assertion or a disabled control is not evidence that the unavailable region disappeared.

## Dialogs close on outside click

All current and future dialogs must support outside-click dismissal, as required by [CLAUDE.md](../../../../CLAUDE.md#弹窗); never add a local false override or a replacement style that disables it. The behaviour lives in `Views/DialogDismiss.cs` as one attached property, `local:DialogDismiss.ClosesOnOutsideClick`, switched on once in `EgDialogSurfaceStyle` (`Theme/Styles.xaml`). WinUI implicit styles match the exact type, so **every concrete dialog type still needs its own one-line `<Style TargetType="local:…">`**; `DialogChromeTests` counts the source's `ContentDialog` subclasses against those lines, and `MoviePilotDownloadDialog` (the only table with local surface properties) keeps its own style and must carry the setter too.

**The press lands on the smoke layer, not on the dialog control.** `ContentDialog_Partial.cpp` (`OnApplyTemplate` → `HostDialogWithinPopup` → `PrepareSmokeLayer`) removes the template's `SmokeLayerBackground` rectangle from `LayoutRoot`, sizes it to the window content and parents it to a **separate `Popup`** opened below the dialog's own popup. A `PointerPressed` handler on the `ContentDialog` therefore never sees a click on the dimmed area: measured 2026-10-30 through the offline inspect probe with a real mouse click, the cover dialog stayed open with no exception and no log line. `DialogDismiss` finds the popup child named `SmokeLayerBackground` with `VisualTreeHelper.GetOpenPopupsForXamlRoot` and subscribes `PointerPressed` on it with `handledEventsToo: true`; a press that reaches it has the rectangle as `sender`, so that path needs no coordinate math.

**Do not unsubscribe on `Unloaded`.** Opening a dialog re-parents it into the popup and raises `Unloaded` immediately after `Opened` (measured 2026-10-30: `Opened` 15:39:45.255, `Unloaded` .265, `Loaded` .268). Detaching there silently removed the handler that had just been attached, and every outside click did nothing while the probe's geometry checks stayed green. Attach on `Opened` **and** `Loaded`, detach only on `Closed`/`Dispose`; the dialog itself keeps the subscription alive through `ConditionalWeakTable`. `DialogChromeTests` pins the overlay wiring and rejects local or inherited opt-outs. `Momoka.DialogDismissTests` compile-links the actual handler and executes close/reopen, handled events, popup isolation and subscription cleanup with inert WinUI boundaries; it is not real WinUI input evidence.

Clicks inside the dialog bubble through `LayoutRoot` and are measured against `BackgroundElement` (the dialog control itself spans the whole window, so its own bounds are not the surface); internal flyouts and `ComboBox` dropdowns are separate popups that open above the dialog, so clicking them neither closes the dialog nor reaches the smoke layer.

Dismissal is `Hide()` only: result `None`, never `Primary`/`Secondary`, and a table's own `Closing` guard (subtitle dialog while a download is in flight) still wins. Runtime coverage: the metadata probe case 「弹窗点外面关闭与字幕弹窗右上角关闭钮」 checks the style, the surface geometry, the overlay (found, hit-testable, window-sized, outside the dialog's tree) and close/reopen; the real press is proved separately against the inspect probe's 「点外关闭（小表）」 button — a real click on a control behind the dialog leaves the dialog gone, the page unchanged, and the pointer log shows `sender=Rectangle` (verification skill).

## XAML traps already paid for

- **Binding `CardItem.RowPoster` does not create image demand.** The music track/wall templates originally only displayed that property, so even a Primary tag produced no image GET. `CardArtwork.Item` now claims and reads for the native Image when it enters the tree, passes the owner's `BrowsePresentation` gate, and releases on item change or a real unload. Ignore recycling phantom `Unloaded` while `XamlRoot` remains; reject a former holder's late release through `CardItem`. Reentry claims again and may synchronously restore the bounded cache. The source-linked `Momoka.MusicArtworkTests` proves demand ownership; `InspectMusicArtwork` separately measures real containers, requests, images and viewport behavior. Simulated 20-container counts do not prove ItemsView virtualization.

Use [WinUI feature guidance](winui-features.md) for binding and control defaults. Analyzer configuration belongs to `Directory.Build.props` and the Shell project: read the actual suppressions and assumptions before changing them. The cases below retain repository-specific evidence; recheck the current source and version before generalizing them.

- **For a mirror intended to stay centered, set and verify `RenderTransformOrigin`.** `ScaleX="-1"` otherwise flips about the top-left by default and can move the picture outside its visible band. The removed `HomeBanner` mirror wings exposed this in September 2026: geometry and stretch assertions passed while the picture was off-screen, and one pixel could not distinguish the scrim from real image content. Current `HomeBanner.Probe` does not assert `RenderTransformOrigin`; the existing XAML origin values and other layout checks are separate facts. When changing a transform, inspect the current assertions and verify both the intended origin and the rendered result; an old probe's coverage is not evidence for today's implementation.

- **The historical HomeBanner layout needed an `ImageBrush` to cover its cell. This is a measured layout case, not a ban on `Image`.** Under `Stretch="Uniform"`/`UniformToFill` WinUI's `Image` sizes itself to the *content* (09-10's banner batch measured "the element is the picture"), and its `ActualWidth`/`ActualHeight` then report the drawn picture rather than the layout box — so a reading taken off them can call a picture that overflows the band "filling it". `HomeBanner` hit both halves on 2026-09-11 while making the photo cover the band edge to edge: with `Stretch="UniformToFill"` the elements measured 1014×570 inside a 1014×341 band, and the screen showed the picture anchored at the band's **top** — the bottom 40% (the flower field) cut off, i.e. not the centred crop `UniformToFill` promises. Writing `Width`/`Height` = the band's inner box changed nothing. Caught by the self-check's own `PictureRead`, not by `Probe` (which had asserted the stretch mode, the alignment and the source and was green). Fix: two **empty** `Grid`s whose `Background` is an `ImageBrush Stretch="UniformToFill"` (its `AlignmentX`/`AlignmentY` default to `Center`, and a `Panel` with a background really does stretch to its cell) — the copy lives in the brush (`((ImageBrush)layer.Background).ImageSource`), and the element's size is then a box worth asserting on.

- **Keep an `ItemsSource` collection instance stable, and choose the update operation for the change.** `ObservableCollection` notifies on item additions, removals and moves; item-property changes need their own notifications. Incremental updates avoid disturbing selection or rebuilding every card. Use `Clear()` plus refill for a genuine whole-list refresh, not every small change. Replacing the collection without the required property notification can leave the binding on the old instance.

- **A hand-written card does not inherit the settings page's row-level switches, and 「隐藏功能下方说明」is the one that already bit.** `SettingRow.NotesHidden` is page-level state (`SettingsViewModel` aligns it on load and on the toggle) and the row templates bind `SettingRow.NoteVisibility` — a card written by hand inside a hosted page sits outside that template, so nothing collapses its note for it. 设置 → 通知's 「通知接管」card was exactly that: the switch was on, the paragraph stayed, and there was no error and no signal anywhere (user-reported 2026-09-30, one day after the card was written). Any future page-level flag that a row template happens to consume has the same shape. Fix pattern: keep the rule in one place (`SettingRow.NotesVisibility`, added that day) rather than copying it into the card's view model; have the view model expose it and re-raise it in `Attach` — navigation re-runs, which is the fresh-reading moment, the same reasoning as "the row's visibility is evaluated when its container lands on the tree"; and give the self-check a reading that compares the real `TextBlock.Visibility` against the flag (there is one, 「通知接管的说明跟着那一开关走」). Scope of that switch: 「各条功能下面的说明」only — card titles, the control, and the page's own intro line stay visible.
- **With the notes gone, the lines between rows are what separates them (2026-10-27, user's words: 「开启隐藏下方说明之后用线条分割每个功能」).** `SettingRow.DividerThickness` returns a 1 px top border only when `NotesHidden` is on and the row is not its card's first row; every row template root binds it with `Mode=OneWay` (rows are added and removed in place, so "first" changes hands) and the colour comes from `EgSettingRowStyle`/`EgSettingBlockStyle` in one place. `SettingSection` re-marks `IsFirstRow` on every `Rows` change. A new row shape that forgets the binding is a row with no separator in compact mode — `SettingsLayoutTests` counts the template roots for exactly that reason. First row excluded because the card's own top edge is the boundary; drawing it there gives a double line hugging the card.
- **One category can own several cards, and an empty one must hide itself.** Since 2026-10-27 every long category is split: 主页 two, 播放行为 five, 音频输出 three, 字幕 three (+ three for 实时字幕翻译), 弹幕 four, 关于 four; 视频输出 was already four. Builders return `IReadOnlyList<SettingSection>` (`HomeSections`/`PlaybackSections`/`AudioSections`/`SubtitleSections`/`SubtitleTranslationSections`/`DanmakuSections`/`AboutSections`) and `ReloadAsync` adds them through `AddCards`. 界面 is deliberately still one card — six rows, and the card is shared with 飞牛's 「外观」 entry, which retitles *every* 界面 section (`ShowCategory`). `SettingSection.SectionVisibility` is `IsVisible && Rows.Count > 0`, so a card whose dependent rows all went away collapses whole instead of showing a title with nothing under it. Keep the section instances stable and update rows in place (`UpdateRows`) — replacing the card throws away focus and half-typed text.
- **A visibility predicate that gains a conjunct on `IsCompact`/`HeroCard` must join `PageWidth`'s notify list — that is one half of its life; `AnnounceShape` is the other.** The 09-12 column/tail split gave `PickersVisibility` a `!HeroCard` half and the list only got `ColumnPickersVisibility`: on the episode page opened wide, the tail pickers evaluated Collapsed and nobody re-asked after the window crossed 1024 — 媒体源/音频/字幕 gone in the narrow window, not one error anywhere (fixed same day; the same batch's `VideoLineVisibility` and `HeroContentAlignment` carried it too). The attribute list on `DetailViewModel.PageWidth` is the tripwire: every property whose getter reads `IsCompact`, `HeroCard` or `IsEpisodePage` needs an entry there *and* a raise in `AnnounceShape`, because each of the two inputs can flip while the other's notification says nothing.

- **A sibling does not inherit another child's inner padding.** When adding a shared background, inspect which children are inside the padded container and which are siblings outside it; check their actual bounds against the background and corners. An earlier `DetailPage.HeroTail` layout mixed a padded `Viewbox` with an episode band outside it, letting the band cover a newly added card's margins. That layout has been retired: current `EpisodePanel` belongs to `BodySheet`, and `HeroTail` no longer contains that `Viewbox`. Keep the padding lesson, but use the current XAML tree when planning a layout change.

- **A deferred `x:Load` target must exist before its named animation starts.** A `Storyboard`'s `TargetName` is resolved against the namescope at the moment `Begin()` runs, and a deferred element isn't in the scope yet, so the animation throws outright. The player's pause-pulse probe (`ProbePulse`) exists to pin exactly this. Before adding `x:Load` to anything to save startup time, confirm no `Storyboard` points at it and no code reaches it by name.
- **Audit named access before deferred loading.** Materialize the element before accessing it and guard its lifetime; otherwise keep it eagerly loaded.
- **Check current container ownership before diagnosing a reparenting race.** `DetailPage.xaml` places `EpisodePanel` first in `BodySheet`; `DetailPage.PlaceEpisodes` only inserts it when that collection does not already contain it. The old hero/body switching path has been removed. Its historical failure was checking `Parent` before `Loaded`, when the property could be unset; if future code really needs early reparenting, inspect the candidate panels' `Children` and handle removal and insertion explicitly. Current `ShellPage.RefreshActive` reloads data on the existing page instead of navigating again. The 「播放回来那一页」 self-check checks the episode container and return scroll position through a simulated UI return without starting playback; it does not establish coverage of a live playback lifecycle.
- **The playback title bar is client area**, so dragging the window and minimise / maximise / close all have to be implemented by the page itself. Don't treat it as an ordinary title bar — the `InputNonClientPointerSource` machinery only covers browse state. Withdrawing a region declaration (`ClearRegionRects`, or an empty array) turns the whole strip permanently into client area, so after watching one film the window can no longer be dragged; the self-check asks `WM_NCHITTEST` about this on purpose. **The frame gives the top edge only 4 physical px (96 dpi) while the sides get 8**, and a playback window parked against the top of the screen has almost no grip; `HostWindow.PlaybackTopResize` answers `WM_NCHITTEST` itself for a DPI-scaled 8 px top band (top / top-left / top-right) while the playback title bar is active. The self-check asks at top+5 as well as top+1 — keep both, or the narrow original band silently passes again.
- **Fullscreen has to be told to DWM as well as to USER32.** `DWMWCP_ROUND` — which the app asks for so the browsing window gets Win11 corners — makes DWM draw a 1 px window border as part of the same frame. Windowed, that line hides inside the window's own frame; fullscreen, where the window covers the monitor and `WS_CAPTION`/`WS_THICKFRAME` are already stripped, it lands as **one line along each screen edge plus a notch at each corner** (measured 2026-10-09 on a white test clip: `#323B48` at the outermost pixel against `#FFFFFF` three pixels in). `HostWindow.ApplyWindowsChrome` therefore picks `DWMWCP_DONOTROUND` while `Fullscreen` is true, and `EnterFullscreen`/`LeaveFullscreen` re-ask DWM after the style change — don't set the corner preference once at creation and call it done. The self-check reads the attribute back in both states (「全屏不带 DWM 圆角与边框」); the pixel evidence lives in the probe, not in the self-check, because screen sampling there would depend on whatever else is on the desktop.
- **Two pointer facts that keep biting.** WinUI raises `PointerMoved` when the content under a *stationary* pointer changes — treat that as real movement and auto-hide never fires. And `PointerExited` fires when the pointer merely moves onto a child of the same control — treat that as "left the window" and the overlay blinks out the moment a hand reaches for it. To decide whether the pointer really left the window, **ask the system**; don't read the coordinates off the event.
- **The historical repeater image pipeline could not use `Loaded`/`Unloaded` alone as item ownership.** The recycle pool raises `Unloaded` on an element that is still painted on screen and `Loaded` never comes back (measured 2026-09-05 on four grey cards, re-measured 2026-09-12 on the home page's grey covers: `Unloaded` fires with `XamlRoot` still set, 3 ms after `Loaded`, and no further `Loaded` ever arrives). Any one-shot work gated on a `_live` flag therefore runs at most once per container — for `PosterCard`/`EpisodeRow` that meant every card later bound to the container *never issued its image request*: title and glyph normal, cover grey forever, and not one log line, because nothing failed. The fix is two rules: start the work in `OnCardChanged` unconditionally (a `Card` assignment has exactly one meaning — this container is about to show this item), and let `OnUnloaded` ask `XamlRoot` instead of believing the event (`if (XamlRoot is not null) return;`). The same shape bites anywhere a container-scoped side effect is triggered from `Loaded` alone.

- **The framework `.pri` files do not merge themselves in — a publish without them produces an app that cannot start, and 「just publish twice」 is a myth.** `Momoka.pri` has to contain the framework's `themeresources`, or the exe dies at `App.xaml` with `Cannot locate resource from 'ms-appx:///Microsoft.UI.Xaml/Themes/themeresources.xaml'` (exit code `0xC000027B`). The chain, measured bottom-up on 2026-09-11: `Momoka.pri` ← `makepri.exe new` ← `priconfig.xml`, whose third `<index startIndexAt="…pri.resfiles">` is the merge entry; `pri.resfiles` ← `@(_PriFilesFromPayload)`, and **that variant reads `@(PriOutputs)`** (`Microsoft.Windows.SDK.BuildTools.MSIX.Pri.targets:243`), **not `@(PackagingOutputs)`** — injecting into the latter does nothing at all, which is the first wrong turn. `PriOutputs` is filled by `GetPriOutputs` and holds only the project's own xbf/content plus `ProjectReference`; the framework PRIs ride the NuGet `runtimes-framework` asset channel and **never enter it**, so `pri.resfiles` is 0 bytes and `Momoka.pri` comes out 103–135 KB instead of 2.2 MB. The three live under each package's `runtimes-framework\win-x64\native\`: **WinUI** → `Microsoft.UI.Xaml.Controls.pri` (2 088 000 B, the one with `themeresources`); **InteractiveExperiences** → `Microsoft.UI.pri` (101 528 B — *not* in the WinUI package, the second wrong turn); **Foundation** → `Microsoft.WindowsAppRuntime.pri` (11 296 B). Fix: `AddWindowsAppSdkFrameworkPriToPayload` in the Shell csproj adds them to `PriOutputs`, and it must hang off **both** `BeforeTargets="_GetPriFilesFromPayload;_GenerateProjectPriConfigurationFiles"` — the latter depends on the former, so a later hook has already lost. **It is not a timing problem and re-running the publish is useless**: four consecutive publishes against a freshly cleaned `bin` all came out 135 KB. The old note in `CLAUDE.md` and the comment in `tools/verify-publish.ps1` both said otherwise and were disproved that day. The target removes missing input paths and warns only when **all three** framework PRIs are absent. One or two missing files do not trigger that warning; verify each resolved package path and the PRI merge inputs after a package change. `tools/verify-publish.ps1` checks the final `Momoka.pri` for `themeresources`, which detects that startup failure but does not prove that all three framework indexes were merged. Diagnose missing inputs from the current package layout and restore state rather than treating the warning as proof of a version change.

- **A `ComboBox` in a content-sized row loses its width the moment its dropdown opens, and the list then lands on the right-hand neighbour.** The framework's `DropDownOpened` visual state zeroes the selected item's `ContentPresenter`, so the box's desired width collapses to `MinWidth`, while the popup is sized to the *widest* item. In a `WrapRow`/`Grid` that sizes by content the row re-lays out, the neighbour slides left, and the wider list covers it — user-reported 2026-10-16 on the movie / series / season detail pages (「选择栏展开后会触发自动收缩导致选择栏与右侧的组件重叠」). Measured offline on a movie page with nine audio tracks (`detail-picker-open.txt`): the box went 44–616 → 44–244 and 44–577 → 44–244 while the list stayed 44–602, and 44–244 → 44–244 when the selected track was short. `EgPicker` now pins its own `Width` to `max(resting width, list width)` on `DropDownOpened` and clears it on `DropDownClosed`; the target is capped by the room left in the parent, so a widened picker still cannot leave its column. Two traps inside that fix: read the resting width from `SizeChanged` while closed rather than from `ActualWidth` at open time (the collapse is already in flight), and note that `Popup.ShouldConstrainToRootBounds` **throws once the popup has been opened** — it can only be set before the first open.
- **Diagnostic tool behavior depends on the current host and permissions.** Check exit codes and actual output files; a quiet command is not evidence it worked. If output capture is unavailable, use an explicitly permitted log file. Do not route a denied command through a `.cmd`, another shell or another agent to bypass the denial.
