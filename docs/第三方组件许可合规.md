## 一、结论摘要

1. **项目里没有 `osc.lua`。** 本项目的播放控件是 **uosc**（第三方独立项目，`LGPL-2.1`），
   加上 **`stats.lua`**（mpv 内置脚本的中文覆盖版）。你原判断中关于 `osc.lua` 的分析，
   对象放错了。
2. **真正的约束不是 Lua 脚本，而是 `libmpv-2.dll`。** 经核实，随包这份 libmpv 是 **GPL 构建**
   （`GPL-2.0-or-later`）。应用在进程内加载并链接它，二者构成同一部作品 ——
   **整个 Momoka 按 GPL-2.0-or-later 分发**，与是否修改 Lua 脚本无关。
3. 你已经做到的部分是对的：uosc 的**修改声明**（`MOMOKA[槽名]` 标记 + `main.lua` 头部清单）
   和**许可文本随包**（`mpv-ui\LICENSE.LGPL`）都已到位。
4. 发行上有一个实质缺口：**发布包里一份 GPL 文本都没有**，而 `libmpv-2.dll` 就躺在 exe 旁边。
   本次已补齐。

## 二、需要修正的三处原判断

| 你的表述 | 核实结果 |
|---|---|
| 「本项目的 lua 脚本播放控件是 osc.lua」 | 项目内**不存在** `osc.lua`。播放控件是 uosc（tomasklaen/uosc，独立项目）；另有 `stats.lua` 来自 mpv。 |
| 「osc.lua 是 mpv 的核心内置脚本，GPL-2+ / LGPL-2.1+」 | 这句本身对，但**指向错了对象**。osc.lua 确实属于 mpv 项目、随 mpv 的默认构建按 GPLv2+ 发布 —— 只是本项目没有用它。 |
| 「只原样调用 → 项目不必 LGPL；修改了 → 修改部分须 LGPL 开源」 | 这条 LGPL 逻辑对，但适用对象是 **uosc（LGPL-2.1）**，而且本项目**确实修改了** uosc，所以修改部分必须以 LGPL-2.1 开源。**这一条已满足。** 但它不是全项目最紧的约束。 |

**被忽略的那条约束**：`libmpv-2.dll` 是 GPL 构建。GPL 与 LGPL 的差别正在这里 ——
LGPL 允许「链接而不传染」，GPL 不允许。所以「改没改 Lua 脚本」不影响结论，
只要链接这份 libmpv，整个应用就是 GPL 作品。

### libmpv 为什么判定为 GPL 构建

mpv 默认按 GPLv2-or-later 发布，只有 `-Dgpl=false` 构建才是 LGPLv2.1-or-later
（见 mpv 仓库 `Copyright` 文件）。这份二进制（mpv v0.41.0-923-g7b8915bc1，2026-08-14，
出自 dyphire/mpv-winbuild）有三条独立证据指向 `gpl=true`：

1. 它的 `--vo` 列表含 `direct3d_shaders` 与 `direct3d`；mpv 的 `meson.build` 把这个视频输出
   门控在 `get_option('gpl')` 上，不满足时报 `"the build is not GPL!"`。对应源文件
   `video/out/vo_direct3d.c` 带 GNU GPL v2-or-later 头，且被 mpv 的 `Copyright` 列在
   「仍为 GPL-only 的文件」中。
2. 二进制内可见 libx264 / libx265 / libdvdcss —— 均为 GPL-2.0-or-later 库。mpv 的 `Copyright`
   明确提示「链接的库同样会影响最终许可（例如 FFmpeg 若按 GPL 构建）」。
3. 包内 Lua 模块（如 `mp.input`）自带 LGPL-2.1+ 头 —— 但**单文件头不覆盖构建级结论**，
   这只是「哪些文件是 LGPL」的信息，不是「这个构建是 LGPL」的证据。

判定依据已写进 `assets/mpv-runtime/NOTICE.txt`，随包发行。

## 六、项目自身的许可证：已选定方案 A

**决定（2026-10-14）：采用 `GPL-2.0-or-later`。** 仓库根已放 `LICENSE`（GPL-2.0 正文），
README 与 `THIRD-PARTY-NOTICES.md` 已声明，发布链路已把 `LICENSE` 拷到 exe 根并由
`tools/verify-publish.ps1` 校验。理由：与现有 `libmpv-2.dll` 一致，播放链路零改动；
商店上架不受影响（见下）。下面是当时的两条路与取舍，留档。

**A. 接受 GPL-2.0-or-later（与当前二进制一致，已采纳）**

- 在仓库根放一份 GPL-2.0 正文作为 `LICENSE`，声明项目整体 GPL-2.0-or-later。
- 继续使用现有 `libmpv-2.dll`，不必改动播放链路。
- 需履行 GPL 的源码提供义务：向接收者提供完整对应源代码。本仓库已公开，在商店列表里
  给出仓库地址即可。
- **商店分发不构成障碍**（2026-10-14 复核）。微软商店现有多个 GPL 应用在架：VLC、Audacity、
  HandBrake（后者的商店文案直接写着 "licensed under the GNU General Public License (GPL)
  Version 2"）。机制上，微软服务协议规定《标准应用许可条款》（SALT）**只在应用未提供自己的
  许可条款时**才适用（"Unless different license terms are provided with the application"），
  GPL 应用自带许可条款，SALT 不介入；微软自己的许可模板里也写了开源例外
  （"except and to the extent required by third party licensing terms governing use of certain
  open source components"）。要做的只是把许可条款与源码地址填进商店列表。

**B. 换用 LGPL 构建的 libmpv，项目保持其他许可**

- 需要一个 `-Dgpl=false` 构建的 libmpv（无 `vo_direct3d`、不链 x264/x265/dvdcss）。
  注意 dyphire/mpv-winbuild 出的是 GPL 构建，**不能直接用**；需另找或自行构建。
- 换了之后，链接不再传染，项目可保持闭源或选用 MIT 等宽松许可。
- 代价：`vo_direct3d` 等 GPL-only 组件消失（对本项目的 D3D11 播放路径无影响），
  但需重新验证起播、硬件解码与着色器链路，并重跑四道闸门。

**B 的一个变体**：仍用 GPL 构建，但只把**项目自身代码**声明为 GPL-2.0-or-later 之外
的许可 —— 这在法律上不成立（整体受 GPL 约束），不建议。

### 判定依据（为什么新的这份是 LGPL 构建）

`--vo=help` 那类清单随 `-Dcplayer=false` 一起没有了，所以改从 libmpv 的日志接口读它自己报的启动横幅：

```
-Dgpl=false -Ddvdnav=disabled -Drubberband=disabled -Dopenal=disabled
-Dcplayer=false -Dlibmpv=true ...
```

三条互相印证：

1. 配置行里 `-Dgpl=false`，且 `dvdnav` / `rubberband` / `openal` 被明确关掉。
2. 功能表里没有 `gpl` / `direct3d` / `dvdnav` / `rubberband` / `openal`。
3. 二进制里 `libx264`、`libx265`、`libdvdcss`、`dvdread` 四个 GPL-only 组件的字符串出现 **0** 次；
   换掉的那份 GPL 构建分别是 5 / 10 / 3 / 6 次。

### 来源核对（一字节不差）

- 发布页 `sha256.txt` 与下载到的归档：`1488b4458279561a4a0134ddf837989dcc8045308ac521657a98a284bcd8529d`，一致。
- 归档解出的 `libmpv-2.dll`：`fe583af3…`，与换入仓库根的那一份逐字节相同。

### 换内核带来的功能差异

Momoka 用到的能力一个没少：`d3d11`、`vulkan`、`libplacebo`、`d3d-hwaccel`、`d3d9-hwaccel`、
`cuda-hwaccel`/`ffnvcodec`、`luajit`、`libass`、`shaderc`、`spirv-cross`、`zimg`、`lcms2`、
`libcurl`、`libarchive`、`libbluray`、`vapoursynth` 都在。少掉的是：

| 少掉的 | 是什么 | 对 Momoka |
|---|---|---|
| `direct3d`（vo_direct3d） | D3D9 视频输出 | 用不到：集成管线走 D3D11/Vulkan |
| `dvdnav` | DVD 导航 | 用不到：没有光盘播放 |
| `rubberband` | 变速时的音高算法 | **有影响**：倍速退回 mpv 自带的 scaletempo，变速照旧可用、音质不同 |
| `openal` | 音频输出之一 | 用不到：走 wasapi |
| `win32-executable` | mpv.exe 那个壳 | 用不到：只用 libmpv |

另外 WebP 截图在换后实测仍可用（LGPL 版 FFmpeg 带 libwebp）—— 这条是本轮特意验的，
因为 Momoka 的截图设置里有 webp 与它的无损/质量/压缩三行。
