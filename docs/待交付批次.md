## 记录口径

- **记产品改动。** 代码、脚本、应用资源的合并批次要记；纯文档合并可以记一行，但验证列写「无」，交付时不额外跑东西。
- **一行一批。** 同一分支的多条提交合成一条；不同分支、不同日期各占一条。批次内小修追加到原条目，不新开。
- **只记已合入 master 的东西。** 还在临时分支、没合并的改动不进台账；合并完成后再补这一条。
- **不写凭据与真实服务器信息。** 地址、令牌、账号一律不记；需要指路时写 PROGRESS 或验收文档的路径。
- **验证列写「要跑什么」，不写「跑过了」。** 分支上的通过报告只覆盖分支代码，交付时一律按主树最终代码重跑；可以在备注里记分支证据的位置，但不得当作交付证据。

## 交付时怎么做

1. 汇总本表所有「待交付」条目的验证列，取并集，去掉重复项。
2. 在主树最终整合代码上依次跑：编译 → 测试 → 受影响运行检查/探针 → 截图；同批发新版本、升级依赖或分析器时加闸门 1 与闸门 4。
3. 全部通过后运行 `tools/publish.ps1 -NoArchive`，核对桌面快捷方式确实指向主树 `artifacts/publish/win-x64/Momoka.exe`（闸门 3）。
4. 把发布日期、发布件哈希与核对结果写进下方「已交付」，再把对应条目从「待交付」删掉。
5. 任一检查失败：修在当前主树并提交，按改动规则补测试；该条留在「待交付」，不发布，不用失败日志冒充交付证据。
