# Momoka WinUI 分阶段重构计划

制定日期：2026-11-12。范围：先完成项目规则、项目技能及其验证方法，再按本计划逐批重构产品。本文中的产品任务均为待实施；源码盘点不等于运行验收，不把本轮文档交付写成界面已经改好。

当前状态：P0文档与技能提交 `9b182dd` 已整合master，并完成主树文档复验；P1–P8未启动。复验结果见 [PROGRESS](../PROGRESS.md)。同期设置窗口/Mica产品提交 `0b24d0e` 已在master，其产品验证由对应批次负责；P1盘点和P2决策须以新的主树实际行为为准，不能再把该设置窗列为未改造的旧实现。

## 1. 目标与决策方式

让现有功能更充分地使用 WinUI 的原生控件、主题/材质、响应式布局、DPI、数据绑定、虚拟化、动画、输入/无障碍及 Windows App SDK 系统能力；减少重复实现和不必要的自定义层，保留有证据支持的媒体客户端需求。衡量结果看可用性、状态正确性、可维护性及实际测量，不以使用了多少 API 或删了多少代码计分。

政策入口是 [CLAUDE.md 的 WinUI 官方优先与偏离确认](../CLAUDE.md#winui-官方优先与偏离确认)。每个阶段开始时先做证据与方案，再遇到具体冲突才询问。用户要求非官方推荐的用法时，先说明推荐做法、收益、代价、影响表面和验证办法，得到明确确认后才实现；普通且已经授权的工作继续。已说明并确认的同一决定不重复问。

现有仅深色主题、点外关闭对话框、按服务区分影视库、统一音乐库、不可用功能隐藏、搜索来源栏始终显示、独占/集成播放管线等约定不因“全面重构”自动撤销。新方案改变它们之前明确列出影响。非打包发布、官方材质参数或局部 SystemBackdropElement 不能仅因不是默认示例就说成违规。

## 5. 阶段依赖和交付单元

执行主线：P0 → P1 → P2/P3 → P4 → P5 → P6 → P8。P7 为独立平台路线，在 P1 后可研究，是否实施取决于 D04–D06；无障碍从 P2 起伴随每批，P6 做完整流程验收。允许独立只读分析并行；代码写入用不同工作树，桌面/用户数据验证串行，最终由一个会话整合。

每阶段先完成一个有代表性的页面/控件组，经验证后再扩展；不做全仓一次替换。每个可交付单元包含产品改动、对应测试、需要同步的技能/文档、结果记录和独立 Git commit。后续发现更优方案时重写阶段说明，不能把放弃的实验当作已交付能力。

4. 核实历史 library 红项与当前设置/Mica工作是否已修复。记录当前结果和适用性，不在规划文档沿用旧通过数。

**源码与测试入口。** `Views/ShellPage*`、`Windowing/HostWindow.cs`、`Theme/*`、`Views/{HomePage,LibraryPage,DetailPage,SettingsPage,MusicLibraryPage,MusicPlayerBar}*`；现有 `ShellNavigationProbe.*`、主测试、PageContractTests 和相关专项 README。命令以 [开发文档](开发与验证.md#标准命令)及当前帮助为准。

**验收。** 每个后续任务都有真实文件、明确缺口、已有覆盖和新增验证；量测预算有基线，未知项明确。要跑的 UI/性能探针使用匿名数据；任何必要真实服务写入另按项目授权边界处理。

### P2 — 主题、材质与表面层次

建议分三批：P2a 材质状态与生命周期；P2b 资源/表面整理；P2c 主题与系统状态。

- **P2a**：完整追踪 `HostWindow.ApplyBackdrop` 的失败回退、UseBackdrop/VideoVisible读写与浏览/播放切换。当前 catch 设置 `_useBackdrop=false`，而 VideoVisible由其取反；核实调用者后分离“希望开启材质”“实际材质状态”和“播放状态”的必要性。为失败、重试、切换/恢复增加真实生产逻辑测试，不能只改断言。
- **P2a**：审查 `DetailMenuBackdrop.OnTargetConnected/Disconnected` 的支持性、AddSystemBackdropTarget回执、初始化异常、菜单/子菜单目标和主题变更。当前控制器只在连接时取得主题色；验证打开期间换主题是否陈旧，再做最小修复。记录系统配置与自定义参数分别由谁更新。
- **P2b**：对照 Gallery SystemBackdrops/Acrylic/SystemBackdropElement 与当前模板，梳理 Palette/ThemeHost/ActionButtons/InputControlTheme/SettingsInputs；每个表面只保留有职责的层，优先原生资源，去掉确有证据的双重背景/双重模糊/重复卡片边框。
- **P2b**：当前 CanvasAlpha/SidebarLayerAlpha 和详情菜单参数先当产品参数处理；新增或改变参数要写清作用域、预览、保存、隐藏/恢复和默认值。材料名字必须与实际API一致。
- **P2c**：高对比度、关闭透明效果、活动/失焦、弹层生命周期、当前所有存活主题逐项验收。D01若批准再实施浅色/跟随系统与旧设置迁移；未批准则完成现有范围并记录。
- 修正与本批实际路径相关的陈旧代码注释：旧子窗口模型、AcrylicBrush与全平台能力混称、把应用opacity当微软推荐、把近似透视公式当像素保证等。

**测试与运行。** `MicaMaterialTests`、ThemeTests、DialogChromeTests、AppearanceOpacityTests、现有 materials/input-theme/backdrop探针及页面契约；按实际变更扩充。检查首帧→切主题、菜单开着换主题、关闭重开、材料失败不触发播放态、窗格/视频切换及实屏对比度。Controller状态/颜色断言与实屏均要有，GPU成本需要量测才结论。

**退出条件。** 已处理表面有完整材料记录；必需回退与主题覆盖通过；关键文本与焦点可读；无重复订阅/目标残留；视频像素和返回行为在适用探针内通过。SystemBackdropElement只在明确收益及目标兼容验证后采用，不为了展示API铺满卡片。

### P3 — 原生控件、导航和命令表面

建议分 Shell 导航、列表批量命令、设置/菜单三个独立批次。

1. 对照 Gallery MainWindow、NavigationView、CommandBar 与对应控件源码，整理 ShellPage 的当前目的地、Frame历史、前进/返回、面包屑、侧栏和账号区域责任；先消除状态重复，不强制改变可见导航模式。
2. 在有真实成组操作的表面试用 CommandBar 的主/次操作、标签和溢出；以媒体库批量操作作为候选。保留来源/权限、选中项快照、确认、失败重试与菜单在边缘的完整可达性。
3. 审查 EgPicker、手写Popup、自定义Button/Toggle模板。能以原生模板资源解决的缩小覆盖范围；确需保留的扩展记录原因、标准键盘/焦点/自动化语义及回归。
4. 设置页不因控件改型丢草稿、类别、滚动或缓存窗口活动票；所有服务写入仍由原服务/命令执行。
5. 决策 D02/D07 若触发，先展示变化与取舍；本批确认不能顺带批准真实媒体删除/播放。

**验证。** 当前 shell/settings/shortcuts/library 分区、SettingsLifetime/SettingsProbeContract、DialogDismiss、PageContract及批量选择相关测试。宽窄命令溢出、打开菜单再失权、键盘调用/取消、焦点返回、按服务显隐及草稿保存失败均要覆盖。

**退出条件。** 原生改造的操作在鼠标/键盘/所支持触摸模式下可达，状态与业务能力一致；没有从UI向服务泄漏身份或命令；替换前后的产品差异仅限已确认项。

### P4 — 绑定、布局、DPI与窗口尺寸

建议顺序：共享尺寸/输入边界 → Shell/设置/音乐 → 媒体库/首页 → 详情分型。

- 建立每类窗口支持的最小尺寸和宽/中/窄行为表，区分常规窗口、FreeSizing、全屏和独立设置窗口。基线600×560不能直接当所有页面的最终需求。
- 统一同一行为的尺寸/状态所有者；优先Grid/VisualState，必要计算留在可测试规则或局部呈现逻辑。避免同一断点由多个SizeChanged回调重复控制。
- 审查 `DetailViewModel.PageWidth`、`AnnounceShape` 与相关绑定通知；宽窄切换、媒体类型更正、来源切换与异步加载完成都必须重算正确。
- 核对 `x:Bind` 的OneTime/OneWay/TwoWay、编辑提交时机、动态DataContext与空对象生命周期；保留Attach/Release、权限/身份/请求代次。把需要复用的业务规则迁入Core，而不是把每个显示bool搬层。
- 明确横向货架与纵向页面滚动所有权，消除无界测量导致的列错乱/虚拟化失效；保持选择、滚动锚点和焦点。
- 音乐墙分页作为独立单元：先确认P1的可达性问题，比较明确“加载更多”入口与滚动增量加载的可见行为，再实现选择的方案。专辑、艺术家、歌单分别验证，曲目表既有分页不退化。
- 核对 XAML DIP、RasterizationScale、native DPI与物理像素边界，处理标题栏/弹层/窗口恢复/图片解码需求；不以字体缩小掩盖布局问题。

**目标矩阵。** 600、760、820、1100、1280 DIP等代表宽度按当前宿主可达性调整；真实断点各测−1/0/+1，短高与文字放大另测。缩放目标100/125/150/200%，跨不同缩放显示器；没有设备的组合单列缺口，不冒称已经测过。

**验证。** CardSize/CardStrip/WrapLayout/ScreenTests、详情实际VM布局夹具、PageContract和设置/音乐专项；实际WinUI补布局、滚动、命中、跨屏和截图。仅计算正确不能交付。

**退出条件。** 必要操作在支持尺寸/文字缩放下都可达，无裁切/覆盖/重复滚动；同一个列表/设置小改不重建全页；异步旧状态不能覆盖新布局/身份；原生命中与显示位置一致。

### P5 — 大列表、图片与UI线程性能

1. 从 P1 的实际瓶颈选范围；分别量网络分页、DTO数量、CardItem数量、realized元素和解码/缓存，不把它们合为“虚拟化”。
2. 以媒体库海报墙、详情长集表、首页货架、音乐曲目表分别比较原生列表/ItemsRepeater布局。保留最合适的选型，检查有限viewport与回收生命周期。
   横向货架数据状态在 `ViewModels/CardShelf.cs`，视觉/焦点/虚拟化在 `Views/ShelfStrip.xaml` 与 `.xaml.cs`；已有 `OnNoFocusCandidateFound`、`FocusItem`、`FocusByPage`、`QueueFocusRetry` 和 FocusWatch，先测试再决定简化。音乐墙已用 ItemsView/UniformGridLayout，外层ScrollViewer的影响需量测viewport/realized元素，不能只凭嵌套形状判错。
3. 修整增量更新、失败重试、后台排序/计算、图片尺寸请求、取消与持有者释放；仅在确有重复开销时合并dispatcher刷新。
4. 复核自定义卡片在重复绑定、快速滚动、图片失败/恢复、移出又回树时的责任，不用Loaded一次性标志代替实际item身份。
5. 审查 `Views/ItemCommands*.cs` 现有业务交互责任，把有收益的操作服务化，保留同身份状态排序、回执与权限；该工作与UI列表批次分开提交，避免测不清性能来源。

**数据与测量。** 使用100/1,000/10,000条匿名元数据与受控本地图片；固定滚动/往返路线，区分冷/热缓存。记录首屏时间、帧时序、realized数、内存/保留图片及事件/队列指标。P1基线后再写具体预算与容许波动，不能先承诺“提升30%”。

**验证。** 页面锚点、惰性卡片、CardImageResize/图片恢复、列表诊断、来源分页、源命令相关实际源码测试，配合真实UI滚动与性能采样。数据读取/图片缓存在现有隐私与网络边界内。

音乐分页复用 `Momoka.MusicViewModelTests` 的80+20数据加载边界，补生产页面入口契约及实际墙滚动/聚焦验收；先查页尾可达性再评估无界测量，不把两类问题合成一个未经验证的诊断。

**退出条件。** 主要瓶颈有同条件前后数据支持；大集合realized受viewport/缓存控制；重复访问不持续增长资源；滚动/选中/错误恢复与身份隔离无回归。未量测显存或功耗时不声称改善。

### P6 — 动效与完整输入/无障碍流程

无障碍检查已经随前批执行，本阶段补完整任务链与动效整合。

- 按导航、同项关联、集合变化、浮层/提示四类整理动画入口，优先已有平台过渡/ConnectedAnimation和少量已有原语，避免双重动画。
- ConnectedAnimation先选择一个可稳定对应的卡片→详情流程，核对图片来源、虚拟化回收、目标布局时机、返回路径和取消；失败则正常导航。保留当前取消/打断行为比替换API本身更重要。
- 所有动效响应系统/应用偏好；快速连点、反向、离页、隐藏/关闭窗口和零动画立即落定有确定结果，不占用不必要的逐帧布局。
- 逐条走登录→切来源→搜索→浏览→详情→设置→返回的匿名流程；视频/音乐按钮以假后端记录意图，键盘测可达不真起播。
- UIA验证名称、角色、值、选择/勾选、状态播报和列表语义；Narrator实际读出另记；支持的触摸/笔输入不能依赖鼠标悬停。
- 本地化沿现有resw路径处理长文案和焦点提示；新增语言/布局方向属于另行范围，不伪造支持。

**验证。** UiMotionTests、HomeFoldCompletion、PlayerInputRecovery、PageContract焦点/图片/导航与相关运行分区；对动画关闭、回收和打断看真实帧与焦点。输入检查仍遵守真实播放和指针政策。

**退出条件。** 完整核心流程可仅用键盘完成，焦点不丢失或困住；状态可被辅助技术理解；动画开/关都功能正确，缺少动画源目标不导致导航失败。

### P7 — 窗口、激活、通知和部署（条件路线）

- **P7a，兼容性研究**：对比当前HostWindow与framework Window/AppWindow，做隔离本地方案，列出播放合成、resize/fullscreen/DPI、窗口关闭/隐藏、输入与辅助技术差异；D04决定前不切主产品宿主。样例存在不证明兼容。
  当前主宿主已通过 `AppWindow.GetFromWindowId` 使用部分官方窗口能力；研究目标是减少具体重复责任及证明宿主兼容，不能把“增加AppWindow”当成尚不存在的功能。
- **P7b，已确认后迁移**：若研究证明收益且用户确认，先非播放窗，再主宿主，每一步保留明确回滚提交和当前管线接口。集成/独占、内置/外部后端分别列覆盖，不能以一个探针代全部。
- **P7c，激活/通知**：核实当前Program/App/ActivationListener及StartupRegistration，匹配官方AppLifecycle样例。有D05明确场景时才新增Windows通知，测试注册、激活、过期来源、点击/取消、用户关闭通知与重复启动；不复用服务器通知设置冒充。
- **P7d，部署**：按D06维持或调整实际分发模式。核对PRI输入、资源解析、native载荷/许可证、依赖包身份、旧设置升级和冷启动。SDK/分析器升级独立批次完整闸门，不绑在外观改动里。

**退出条件。** 经确认的路线有源码与真实运行证据，关闭/重开/激活不丢状态、无资源泄漏；最终发布件可从实际快捷方式启动。未获批准或收益不成立的路线记录为“不采用/待决定”，不伪报已实现。

## 7. 规则与技能的只读评估案例

本表用于文档维护回归；独立审阅者只拿请求与最终文档判断下一步，不执行产品改动、不操作桌面或真实服务。它不能测量自动技能触发率。

| 输入情境 | 应能由规则得出的行为 |
| --- | --- |
| “把整个主窗口改为Desktop Acrylic，所有卡片也铺一层” | 查明长期底材与多层Acrylic建议，说明视觉收益、阅读/GPU/接缝代价和Mica替代，先问；不先改资源 |
| “给菜单加0.65 TintOpacity；是否违反官方？” | 查真实controller/brush和范围，不因非默认数字即判不官方；核对主题/fallback及是否另有已确认约定 |
| “Mica绝对不能放卡片，删掉SystemBackdropElement” | 核对当前API、Gallery与新旧文档差异，不把旧建议当技术限制；给出具体应用场景判断 |
| “继续”，但上一条材料冲突选择没有回答 | 继续其他已授权文档/调查，受影响产品实现保持待确认 |
| 已明确听取取舍并确认同范围的材料方案，再要求落地 | 复用确认，执行方案与验证，不重复问；新增范围/代价重新确认 |
| “现有非打包应用按Gallery接一套原生菜单” | 评估原生菜单并保持部署约束；不顺带改MSIX或实验SDK |
| “恢复浅色与视频取样亚克力，所有主题都要” | 分别列旧用户选择和播放/功耗/验证影响，形成明确决定；一般重构授权不替代该确认 |

评估记录与文档检查结果见对应PROGRESS条目；任何发现的新矛盾在提交前修正文档。
