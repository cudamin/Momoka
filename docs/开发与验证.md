主页「有没有新入库的东西」有两条路，**快路径 + 兜底**（2026-10-16 用户令「有新媒体入库时主页不会自动刷新」）。兜底是定时问出来的：主页活着的时候每 30 秒向每个在线来源问一次最新的一小批（`Users/{uid}/Items/Latest`，`LatestSize` 条），折成指纹（`LibraryWatch.Stamp`）和上一次整页重读时记下的比一比，**变了才走 `LoadAsync`**（货架和轮播一起换 —— 用户 2026-10-16 选定；没变也重读等于每半分钟把一页海报连轮播全拆了重装）。从别的页面返回本来就会重读一次（`ShellPage.RefreshActive`），这一档补的正是「就停在这一页上」。钟在 `HomePage`，离页即停，播放层占着窗口的那一段不发；这一趟失败静默（只记一条日志，不弹提示条），读不出来的来源不参与比较（多账号聚合时不拿少了的那一份当「变了」）。**这一趟也是「隐藏的行不联网」的一部分**：轮播关着、继续观看／接下来看／各媒体库那几排又都收着的时候，主页上没有任何东西会跟着新入库换，问那一句没有意义 —— 判据是 Core 的 `HomeLayout.CanRefresh`（2026-10-18 补，此前无条件问，探针「隐藏首页行不请求」当场抓红）；媒体库那一排装的是「这台服务器有哪几个库」、两条 MoviePilot 订阅装的是 MoviePilot 那边的账，都不算。判据在 Core 有单测（顺序敏感、按来源分开、认不出的条目跳过、失败来源跳过）；**运行面没有专门的探针用例** —— 30 秒的钟落在探针用例的时限之外，自检与探针覆盖的都是「重读之后这一页长什么样」，不构成「新入库 30 秒内会自己出现」的证据。

快路径是服务器推的（2026-10-17 用户令，参考 Emby Theater）：`EmbyRealtimeWatch` 给每个在线来源各开一条 `EmbyRealtimeConnection`，连 `/embywebsocket`（`EmbyRealtimeProtocol.Build` 拼地址：`http(s)` 换 `ws(s)`、路径接在反代前缀后面、`api_key` 与 `deviceId` 进查询串），**被动等 `LibraryChanged`**，收到就立脏位、排一拍、复用上面那条 `AutoRefreshAsync`（快路径和 30 秒那一趟走的是同一条路）。**一条都不订阅**：真机实测这台服务器在播放期间每 2 秒推一条 `Sessions`（90 秒窗口 21 条），订阅它等于看片的时候主页一直在重读；Emby Theater 订阅 `Sessions`／`ActivityLogEntry`／`ScheduledTasksInfo`／`SessionEvents` 四类，是因为它的播放器状态也走这条通道，Momoka 要的只是「有没有新入库」。`UserDataChanged` 同样不算（观看进度那一路归播放返回那一趟管），`RefreshProgress` 也不算（扫描进度条，扫一遍发十几条）。断了按 `EmbyRealtimeBackoff` 退避重连（1、2、4…30 秒封顶；连上过一次归零）—— 比 Theater 自己的 WebSocket 多这一层，Theater 的 `onclose` 只置空引用、重连靠外部事件推（`onAppResume`、`onNetworkChanged`、任何一次 HTTP 请求失败后跟的 `ensureWebSocket`），而 Momoka 主页不像它那样持续发请求，没有那个外部事件可依赖。通道跟着页面寿命走（`Attach` 开、`Cancel` 收），比 Theater 的全局常驻收得紧。**这条通道是快路径、不是替代品**：连不上、或者服务器不推 `LibraryChanged` 时，行为等于没有它，30 秒那一趟照旧。地址拼装、消息判定与退避序列在 Core 有 12 条单测。

## 架构

Scope捕获的Connection/令牌/媒体身份不跟随权限变更，当前IsAdministrator/PermissionRevision另读在线identity；同身份确认新client使能力缓存与管理旧请求失效并通知现有设置/四飞牛管理页。降权完整隐藏及执行拒绝，升权入口恢复；账号保存不订阅管理权限寿命，R010本地保存监控分开保留。插件/Probe/管理await跨revision不回填，显式非默认来源按自己的scope核，旧已发送服务端写不能因取消而宣称撤销。

### 共享设置保存与飞牛改密欠项（R-010，2026-10-24）

`SettingsStore` 统一记录所有调用者的保存结果，`ISettingsService` 经窄 `ISettingsPersistence` 暴露本地重试和通知。会话直接保存失败也使当前设置页/密码页显示完整欠项区；缓存设置页只 `SyncSaveState`，不 Reload 或重建草稿。服务器确认改密与本地持久化分别提示，“重试本地保存”只保存现有内存文档，不再发送改密请求、不启用 Remember、不复活来源，也不提交输入框的新草稿。通知可能来自后台，页面按活动票切回 UI，隐藏/离页退订、旧队列拒绝。

### 代码签名与 SmartScreen

交付件没有代码签名时，从网上下载它的人第一次双击会看到「Windows 已保护你的电脑 / 发布者未知」。三条事实决定了这事的做法，按微软现行文档核实（[Code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)、[SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)）：

1. **SmartScreen 一般只评估带「来自互联网」标记（MOTW / `Zone.Identifier` 流）的文件**，「本地构建的 exe 被拦」先拿流列表核实，别照猜处理。但要留一手：2026-10-01 本机实测三轮，交付件全程无 MOTW 仍被拦——文档说的是一般行为，不是本机判定器的完整判据，别把「无标记」当「必然不拦」的证据。
2. **自签名证书没用。** 官方口径是自签名的 SmartScreen 行为**与不签名相同**：签名者不是受信任根，Windows 照样报「发布者未知」。拿本机自签证书签交付件只增加一层看起来安全的假象，唯一作用是本机 `signtool verify` 能过（MSIX 旁加载需要它），不解决提示。
3. **证书也不等于立刻免提示。** OV／EV 证书首个版本仍可能提示，信誉按同一个发布者身份随下载量累积；EV 自 2024 年起不再免检。真免提示只有两条路：CA 签发的证书（¥千元级/年，中国大陆个人走传统 CA；微软 Azure Artifact Signing 不对中国大陆个人开放）或上架 Microsoft Store（微软代签，但需开发者账号与审核）。换证书会让已有信誉清零，签名身份要一次定死。

本机消除下载件的提示用 `tools/unblock-momoka.ps1`：只摘 Momoka 自己那些文件的 MOTW，先清点后动手。

```bash
powershell -NoProfile -File tools/unblock-momoka.ps1           # 只看会动哪些
powershell -NoProfile -File tools/unblock-momoka.ps1 -Apply    # 真摘
```

两个坑写在脚本注释里，也值得在这里留一句：受限沙箱终端对工作区外的写入会被**静默忽略**，`Unblock-File` 会「成功退出但标记一个字节没少」，所以脚本不复用它的返回值判定成败，而是**读回流列表**；换普通 PowerShell 窗口重跑即可。另外 Inno Setup 写进 PE 的版本字符串是定长补空格的（`ProductName` 实际是 `"Momoka"` 加四十多个空格），按产品名认文件必须先 `Trim()`。

**给交付件签名**（本机自用或企业受管分发场景）用 `tools/sign-release.ps1`：

```bash
# 建证书并装进本机受信任存储，管理员终端只需一次
powershell -NoProfile -ExecutionPolicy Bypass -File tools/sign-release.ps1 -Setup
# 之后普通终端签名（文件或整个目录）
powershell -NoProfile -ExecutionPolicy Bypass -File tools/sign-release.ps1 -Path artifacts\publish\win-x64\Momoka.exe
# 看现状：证书、受信任存储、链能不能建起来
powershell -NoProfile -ExecutionPolicy Bypass -File tools/sign-release.ps1 -Status
```

signtool 从 NuGet 的 `microsoft.windows.sdk.buildtools` 里取（这台机器没有 Windows SDK）；签名默认带 DigiCert 时间戳。**两条代价说清**：① 自签证书只对本机有效——证书装进 `LocalMachine\Root` 之后，这台机器才把它当可信发布者，别人的机器上行为与不签名相同；② **签名会改交付件的字节**，`artifacts\publish\win-x64\Momoka.exe` 的 sha256 此后不再等于 `obj` 里那份重编产物，仓库原先"发布件与 obj 逐字节一致"的复核口径对**这个文件**不再适用，要按"已签名"解释。

签名不必然消掉提示。本机「双击本地构建的 exe 也被拦」一案（2026-10-01）的**真凶是目录上的低强制完整性标签**：`C:\Users\89400\Momoka` 曾带 `Mandatory Label\Low:(OI)(CI)(NW)`，全树继承，urlmon 查安全描述符时把低完整性本地文件判为 Internet 区——与 MOTW、签名、发布者商店、SmartScreen 各开关**全部无关**，改名甩不掉、显式盖 `ZoneId=0` 的 ADS 也压不住。**判别命令一条**：`icacls <路径> | findstr Mandatory`；**修复一条**：`icacls <目录> /setintegritylevel (OI)(CI)M`（继承自动传播，无需提权）。标签来源见下面一段，症状复发先查它。

**标签来源（2026-10-20 查明）**：DSH 的 Windows ACL 沙箱在**工作区写入**（workspace-write）模式下，每次授予写权限都用同一次 `SetNamedSecurityInfoW` 给工作区根目录写入常驻 Low 完整性标签（与能力 SID 允许 ACE、父目录删除拒绝一起），`dispose()` 有意不撤销；该包 README 把「常驻 Low 标签会活过 DSH」列为已知限制，它自带的 ACL 诊断技能也明确**不修** Low 标签。因此只要在这个工作区用过工作区写入模式，标签就会留回来，之后构建/发布的 exe 全部继承，双击被 SmartScreen 判成 Internet 区。本机 DSH 桌面配置的默认档是 `danger-full-access`（完全权限），只有切到「工作区写入」才会写这个标签——**构建、测试、发布建议用完全权限**；若用过工作区写入，双击或交付前先查标签并恢复 Medium。

**用完工作区写入先查标签再构建**：构建前先跑 `icacls <工作区根> | findstr Mandatory`，看到 `Low` 就先 `icacls <工作区根> /setintegritylevel (OI)(CI)M` 再开始构建；标签按继承扩散，构建中途新产出的 exe/dll 都会带上它，事后再查容易漏。

工作区 ACL 上还会看到各沙箱工具留下的常驻授权条目（本机有 `SB\CodexSandboxUsers` 与 DSH 派生的准入 SID），它们不是标签来源，也不要手动删——删了会弄坏对应工具的隔离授权。

SmartScreen 各层开关的事实（应急时用，均与本案根因无关）：用户层落点是 `HKCU/HKLM\...\Explorer\SmartScreenEnabled`（**值不存在 = 默认开启**；`-SetShellSmartScreen Off|On` 写/删它，不需管理员）；策略层硬开关 `HKLM\SOFTWARE\Policies\Microsoft\Windows\System\EnableSmartScreen`（0 = 对所有用户关闭）；`AppHost\EnableWebContentEvaluation` 两处与 `Safer\CodeIdentifiers` 发布者登记对提示**无效**（实测），别再走。

**对照方法**：用 `ShellExecute` 起进程比 `Start-Process` 更接近"双击"；`cmd start` 那条路**绕过**检查，不能用来判断；`ShellExecute` **返回 ≠ 放行**（实测返回了进程没起），判定看进程在不在。追踪判定来源用 Procmon 对比「Internet 判定」与「MyComputer 判定」两个进程的操作差集——本案唯一分歧点是 `QuerySecurityFile`，由此锁死完整性标签。

关掉 SmartScreen 类开关是**关防护**，必须用户同意；本案结束后各开关已全部恢复出厂。
## 视频输出的隔离验证边界

`VideoOutputTests` 覆盖规范选项拼法、HDR 成套临时菜单、四种整数亮度（与小数对比度分开）、元数据组合、设置快照和链前置条件；`ShaderTransactionTests` 覆盖切链拒绝/异常、缺默认值、缺旧值、回滚失败、代次变化与并发。它们是 Core 规则/假后端，不证明 shader 编译或 HDR 显示正确。

实际控件检查需独立宿主：只创建临时默认设置，不走普通 App 启动/真实账号；需要会话的夹具必须拒绝 HTTP 且禁止起播。`--show-settings` 仍是普通路径，不能当离线探针。当前未新增产品级视频探针开关。

原生核对分两种：无媒体句柄读取选项/default/profile/list 并运行切链服务；本地合成视频用 `vo-passes`、渲染日志和截图验证真正执行的算法。文件列表格式化文本会丢分号转义，回滚使用无损节点/JSON列表；单个空路径与空列表都没有 shader，不能把它当属性不可读。固定全屏选档和实际窗口门控是不同尺寸，pass缺席可能是门控，不一律是编译失败。

普通闸门4、真实HDR显示器、杜比素材、外部真实mpv或uosc端到端仍分别验收；不以无声/无窗口采样替代。

## 音频输出离线验证

## 自检与冒烟

`--self-check` 使用诊断窗口构建、布局并绘制页面与播放器合成状态，不加载影片。检查范围包括窗口几何、标题栏命中、浮层显隐、主题资源、设置模板、列表导航、详情页、字幕字体（设置页那一张，播放页那颗搜索框 2026-09-27 已退役）以及着色器档位；当前检查名以源码和 `selfcheck-baseline.txt` 为准，不在文档维护检查数量副本。

普通自检可能复制保存的账号设置并登录真实服务器，读取真实媒体库。它不是离线探针；缺账号、缺素材或无法走到某项检查时的“信息/跳过”也不等于通过。

自检在全新目录使用设置副本、日志、缓存和 WebView 数据，不执行生产目录迁移，不写回真实设置或备份。副本按非最大化运行，生产应用的窗口偏好不变。同一用户的自检用互斥防止跨树同时操作桌面；其他 UI 验证也须自行串行安排。

自检不在日常批次收尾的必跑范围内：只在发版、升级依赖/分析器或用户明确要求时运行，不随每个小修重跑。同一环境已归因的红项，在相关代码与运行环境未变时不重复全量运行，但报告仍按红项如实列出；要得到绿色结论须换满足条件的服务器或环境，不能靠反复运行碰运气或改基线。

`selfcheck-diff.ps1` 把隔离目录放在当前树 `artifacts/selfcheck/<运行标识>`，报告位于其中 `logs/selfcheck-shell.txt`，控制台输出确切路径。直接启动自检时会另建唯一运行目录；可通过 `--self-check-data` 指定尚不存在的本地目录。目录中可能保留 DPAPI 设置副本和真实库读数，**不要提交或公开上传**。

```bash
./artifacts/publish/win-x64/Momoka.exe --self-check --dump-ui
```

`--dump-ui` 在同一运行目录的 `logs` 中输出最后一页的 `selfcheck-shell.png` 与 `selfcheck-shell-tree.txt`。首页媒体库卡片实现后，还输出 `selfcheck-library-card-Normal.png`、`selfcheck-library-card-PointerOver.png`、`selfcheck-library-card-Pressed.png`：直接切换外层按钮模板的常态、悬停和按压状态，拍完恢复，不移动鼠标、不触发点击或播放。`卡片悬浮按钮` 检查同时读取外层按钮三态的实际背景，防止名称后面的白底回归。PNG 不合成 Mica，也不包含系统光标，不能替代真实屏幕截图或光标证据。

### 逐行比报告：每次都会变的行

自检基线比较**检查名与状态**，不比较详情中的每个数字。时间、窗口/光标句柄、线程号、计时、服务器条目与诊断日志数量等读数可能变化，但仍需结合对应断言理解：不能仅因数字曾变化就把失败划掉。

已有报告可单独比较：

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File tools/selfcheck-diff.ps1 -Log work/log.txt
```

确认新增或合法重构的检查后才更新基线：

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File tools/selfcheck-diff.ps1 -UpdateBaseline
```

基线只存状态和检查名，重复的展示项由其所属检查覆盖；任何失败都要保留为红，不能被同名的通过行覆盖。缺失或不完整的报告、未验证来源的旧报告，不构成本次验收。更新基线前按主规则逐项复核，已知旧失败也不能通过更新基线豁免。

「通知页面」「通知确认框」「通知接管那一格」「通知接管的说明跟着那一开关走」四项只有 Emby 有对应页面；Jellyfin、飞牛影视与 Plex 没有通知管理页。自检在这类服务器上写同名的 `[跳过]` 行，基线因此存为 `跳过`；在 Emby 上仍写 `[通过]`，比较器只把「通过 → 信息/跳过」判降级，反向升级不算回归。2026-10-19 的基线按这一条复核过，其余通知以外的检查没有放宽。

做版本对照时保留两份报告并核实产物确实位于改动前后，同时记录账号、库数据、窗口状态等运行条件。相同症状曾出现不等于本轮没有加重，两个文件哈希不同也不证明时间先后。具体判断方法见验证技能。

`smoke.ps1` 只启动应用、等待并报告进程是否仍活着；普通启动仍可能读取真实账号／媒体库，存活不是页面、登录或播放验收。早退出（包括退出 0）、启动失败和日志读取失败都返回非零；非零早退出保留实际子进程退出码及本次新增日志。默认不强停被测程序，检查后由调用者正常关闭：

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File smoke.ps1 -Release
```

只有明确允许清理本次启动的隔离实例时才加 `-StopAfterCheck`，它使用保留的本次进程句柄，不按任意 PID 强停。不能把这个开关当作关闭用户原有进程的授权。`-Seconds` 接受 0～3600 秒，非法值在启动前拒绝。

smoke 的离线回归会在本树临时目录编译 .NET 10 Console 夹具，以假的 `LOCALAPPDATA` 验证 exit 7／exit 0、存活、显式清理、缺程序、坏日志和负等待时间；不启动 Momoka、不读取真实日志，也不替代产品运行检查：

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File tools/test-smoke.ps1
```

## 数据与路径

设置左栏的「Momoka」组永远在最上面（本机偏好、服务器连接、诊断、通知；Emby 的「控制台」不在这一组）。Emby 管理员在它下面再看到照网页端管理菜单分出的「Emby Server／设备／高级」三组：固定条目加上服务器插件页（`web/ConfigurationPages`），CustomCssJS 插件页不列（只过滤菜单，服务器上的插件本身不动）。Jellyfin 管理员看到的是它自己的五组「服务器／设备／电视直播／插件／高级」：控制台、常规、用户、媒体库（显示／元数据／NFO 设置）、播放（转码／继续观看／流媒体／特技播放）、设备、活动、电视直播、数字录像机、我的插件、目录、网络、API 密钥、日志、计划任务，插件配置页接在「插件」末尾，「媒体资料管理器」接在「高级」末尾。两套目录来自 `ServerSettingsMenu` 与 `JellyfinServerSettingsMenu`，文案、路由和插件位置不混用。飞牛影视作为唯一在线服务器时左栏在自己的「帐号」「影视服务器」两组里列出七项：修改密码、播放偏好、外观、媒体库、用户、设置、任务计划（后四项只对管理员）。前两页与四张服务器页是 WinUI 原生页，外观复用「界面」卡；服务器组随管理员身份来去，帐号组对所有飞牛账号可见。Plex 没有管理入口。切换服务器或账号后重新计算，失效页面退出；切换产品时按新产品重建右半边的控制台。
两家的服务器页都是沉浸式的：设置窗口自己的页头、边距和卡片壳撤掉，网页内容铺满右半边；网页端自己的顶栏、底部标签栏、抽屉和页脚由本地注入脚本收起。控制台在同一个 WebView 里换页（两家的网页端都暴露 `Emby.Page.show`），不再每切一次都整页重载；只有第一次进入、设置窗口隐藏后重开、或从 Momoka 卡片切回服务器页（WebView 已释放）时才会走一次启动画面。两套皮肤分别按各自网页端的结构注入：Emby 用 CSS 变量改网页主题，Jellyfin 直接覆盖 MUI／旧版表单的类名；字体、卡片、输入框、下拉、开关、按钮、滚动条都按 `ThemeHost` 当前配色，网页底色取窗口色、卡片取面色、无描边、12px 间距，不写服务器偏好。
`--show-settings 控制台` 打开当前服务器的控制台（Emby／Jellyfin），`--show-settings 网页控制台` 是两家的兼容别名，同样落到「控制台」；`--show-settings 通知` 打开 Emby 的通知条目页。飞牛影视作为唯一在线服务器时，`--show-settings 修改密码／播放偏好／外观／媒体库／用户／设置／任务计划` 分别落到它自己的原生页或「界面」卡；其中服务器四项仍要求管理员，非管理员或权限未知的账号看不到。Emby／Jellyfin 的「用户」「媒体库」等旧名不再对应入口，给到这些名字会退回主页。

普通应用数据位于 `%LOCALAPPDATA%/Momoka`：`settings.json`/`settings.backup.json`、`logs`、`cache/images`、`screenshots`、`webview2`。正常模式对损坏设置执行隔离与恢复；自检不能借此修改生产文件，只能在自己的副本中工作。

正常读取会有界拒绝显式 null 的服务器档案 `Id` 及账号 `Id`／`Username`／`UserId`／两项受保护凭据字段，将原主文件完整隔离后恢复有效备份；没有可用备份才回默认。合法缺键、空串与有意可空字段沿用旧约定，不凭空生成新身份或清空坏字段来掩盖备份。严格读取／导入只拒绝，不写入或隔离其输入。`SettingsTests.AccountNulls` 使用临时配置和假保护器验证这条读取链，不能当作真实 WinUI 登录页启动通过。

正常启动先经 `SettingsStore.PrepareStartupData` 决定是否迁移旧目录：已有当前主文件不迁移；主文件缺失但当前备份按同一正常读取规则可读时，留在当前目录恢复，旧副本不能盖住新备份。当前备份损坏或暂不可读才允许原有旧目录回退，保留旧源和当前备份，不只凭备份存在封死恢复。该准备入口不用于只读自检；`SettingsTests.DirectoryRecovery` 组合验证实际准备入口与 `Load`，没有运行真实用户数据目录。

外部 mpv 路径在「设置 → 播放器」配置；内置后端使用随程序分发的原生库与资源。内置后端下「设置 → 播放器」始终有「自定义 mpv.conf」卡（用户令 2026-10-16）；其中只有独占模式可以选择并填写路径，集成模式下这一项固定为关、显示为只读文字，外部后端整张卡隐藏并忽略这项偏好。独占模式下关闭开关时路径行隐藏，切回后保留原值。

自定义文件覆盖常规音视频设置，下次播放生效；`~~/` 在临时副本中展开为原配置目录，本地 `include` 同样处理，原文件不改。窗口、认证、日志、观看记录和脚本装配仍由 Momoka 管理，不自动载入目录中的 `input.conf` 或脚本。启用后换集重建播放窗口，重新读取配置和条件配置组。mpv 会忽略个别无效选项；配置缺失或不能读取时明确拒绝起播。

`--probe-shell` 的自定义配置宽窄用例使用真实开关、路径框和管线选择器，验证开关关闭、集成隐藏、独占恢复、重入和外部后端隐藏，截图为 `settings-custom-config-*-screen.png`。该入口只验证设置页，不播放视频；真实配置读取与独占播放须另用隔离本地素材验证正式 `LibMpvBackend`。

## 本机工具与故障排查

- **SDK**：用用户级 `.dotnet/dotnet.exe` 按 `global.json` 核实；PATH 曾有旧 SDK，不以旧版本判断环境可用。单节点要求来自本机 workload 解析器曾间歇性无输出失败，不因此断言每次失败都是解析器。
- **Python**：用 `py`；PATH 的 `python`/`python3` 曾被 Store 存根遮蔽，静默退出不证明执行成功，版本以当场查询为准。
- **PowerShell**：源码使用 UTF-8 BOM、LF，兼容 Windows PowerShell 中文解析。终端若错误解码输出，可对该进程设置 UTF-8 输出编码；不要靠重写源码来修终端显示。
- **读取与转义**：优先专用读取/搜索工具；本机曾有遮蔽系统命令的 shell 函数，异常行号先核实实际命令。复杂内联脚本优先改为文件，检查实际命中而非只看退出码。
- **构建环境变量**：`tools/build.cmd` 是旧沙箱缺少 Windows 环境变量时的兼容入口，不是默认必需步骤；只有确认该问题才使用。其 `test` 入口也会先编译，不能用作跳过编译的捷径。
- **WMC9999**：曾由 WinUI 标记编译缓存引起，也曾报过期源码位置。保留输出后可原样重试一次；持续失败正常定位，不能凭错误码断言不是 XAML 问题或盲目清空输出。
- **PRI**：发布件缺 `Microsoft.UI.Xaml/Themes/themeresources.xaml` 时检查 Shell 的 `AddWindowsAppSdkFrameworkPriToPayload` 与发布校验；框架资源缺失不靠“再发布一次”解决。升级包后重新核实合并载荷。
- **截图与指针**：`tools/shot.ps1` 捕获真实屏幕，`--dump-ui` 不合成 Mica；普通 GDI/UIA 截图不含鼠标。光标使用 `cursor-watch.ps1` 的读数及叠加图，机制、授权和失败证据见验证技能；权限拒绝不能换工具绕过。
- **GitHub 匿名接口的 403**：本机走系统代理（`HttpClient.DefaultProxy` 解析出 `127.0.0.1:8686`）出去，出口 IP 是共享的，而 `api.github.com` 对匿名请求只给每个 IP 每小时 60 次；用光就答 403，响应头 `Server: Varnish`、`X-RateLimit-Remaining: 0`，正文写明 `API rate limit exceeded for <IP>`。2026-10-14～16 的更新检查每次启动都撞在它上面。**先读正文与那两个响应头再下结论**：同一时刻绕开代理直连是 200、还剩几十次，`github.com` 的网页与 Atom 源也正常 —— 所以它既不是 GitHub 被封，也不是请求写错了。额度按小时重置，共享出口意味着很快又被用光，别把它当成「重试一次就好」。
