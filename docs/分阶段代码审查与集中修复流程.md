# 分阶段代码审查与集中修复流程

创建日期：2026-10-20。适用于 Momoka 的专项或全项目审查。

**流程：规程校准 → 固定基线与计划 → 分阶段只读审查 → 保存交接并自动推进 → 汇总复核 → 按授权分批修复 → 最终验证。**

本文是审查的组织指南，不是某一轮的审查报告，也不表示代码审查或修复已经开始。项目现行规则以 [CLAUDE.md](../CLAUDE.md) 为准，命令与操作以 [开发与验证](开发与验证.md) 为准，专项方法按当前仓库技能执行。本文不另立安全、验证、提交或发布政策；有冲突先记录并说明，不擅自改规程。

## 一、核心约定

1. **审查和修复分开。** 审查阶段不顺手改业务代码、测试实现、资源、工具或规程；可以写审查记录，并执行符合安全边界的既有离线检查。
2. **按业务链路和风险分阶段。** 不只按文件夹切块；每阶段检查入口、状态、外部交互、结果与清理路径，并安排跨模块复核。
3. **每阶段独立收尾，审查可自动推进。** 已明确启动的审查按本轮计划执行；每阶段保存交接、完成检查与提交后，可自动进入满足前置条件的下一只读阶段，无需逐次询问。可按需开启子代理、使用实际可用的上下文压缩功能；用户要求暂停、范围不明或出现安全风险时停止。
4. **“继续审查”不等于“开始修复”。** 修复范围由用户明确授权；没有授权时，只报告问题及建议。
5. **问题要有证据。** 不凑数量，不把风格偏好、理论风险或缺少某项测试直接当作已确认缺陷；区分已确认、待验证与排除项。
6. **严重风险及时报告。** 疑似或已确认的凭据泄露、身份越界、数据破坏等风险不等全部阶段结束；说明证据和不确定性，停止受影响的危险操作，不自动扩大修复权限。
7. **集中修复不是一个大改动。** 汇总后去重、排除误报、理清依赖，再按相关问题分批修复、补测试、提交，最后统一验证最终代码。
8. **保护已有工作。** 不覆盖、撤销、暂存或提交其他任务的改动；同树写入和并行工作遵守项目协作规则。子代理按明确范围分工，汇总者复核结论；自动推进不意味着扩大产品修改、真实数据操作或发布权限，也不默认创建定时或后台续跑任务。

## 二、阶段与出口

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| 0：规程与技能校准 | 核对现行规则、技能清单、适用范围和冲突 | 已记录权威来源、冲突与处理边界；不修改规程 |
| 1：基线与计划 | 固定受审版本、明确范围、分组和验证办法 | 已保存基线、阶段计划、排除项与每阶段出口 |
| 2～N：分阶段审查 | 按批准范围检查业务链路，收集并复核问题 | 当前阶段范围已检查；问题与覆盖缺口有记录 |
| 汇总复核 | 去重、排除误报、复核过时证据，整理修复顺序 | 已形成带优先级、依赖和验收办法的候选修复清单 |
| 分批修复 | 按用户批准清单实施最小必要改动、测试和提交 | 本批修复及对应检查完成；剩余问题状态明确 |
| 最终验收 | 对最终代码完成适用验证，汇报处理结果和缺口 | 必需检查通过；交付、推送或发布按实际授权执行 |

**每一行都是独立阶段；分阶段审查和分批修复中的每个子阶段也单独保存交接。** 只读审查可按计划自动推进，不能用并行或压缩跳过阶段出口；汇总完成后先报告修复清单，不能自行进入修复。

阶段未完成但上下文不足时，先保存“进行中”的中途交接；有实际可用的压缩功能时压缩后恢复，没有则如实交接并结束当前响应，不把检查了一部分写成阶段完成。

## 三、阶段 0：核对规程与技能

先核对下列来源，不从历史聊天或旧报告推断当前规则：

- 用户本次指令与适用的 `AGENTS.md`。
- [CLAUDE.md](../CLAUDE.md)：分层默认值、安全、验证、Git 与协作要求。
- [开发与验证](开发与验证.md)：本次实际可用的命令、工具和操作边界。
- 仓库内专项技能清单；审查 C# / XAML 前读取 [Shell 技能](../.claude/skills/momoka-winui-shell/SKILL.md)，涉及检查与验收时读取 [验证技能](../.claude/skills/momoka-verification/SKILL.md)。
- [PROGRESS.md](../PROGRESS.md) 中与本次范围有关的在途工作和历史证据；历史记录不替代现行规则或本次源码。

首阶段核对技能的存在、职责、重叠与适用范围；对应阶段开始前再细读专项技能及必要引用，不一次加载所有技能。

发现规则冲突、技能过时或工具与说明不一致时，记录“冲突位置、当前证据、影响、待确认事项”。不要直接改规则让代码合规，也不要把“没有遵循某种默认写法”自动列为缺陷。

## 四、阶段 1：固定基线与制定计划

### 1. 基线必须包含工作区状态

在当前工作树确认：

```powershell
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short
git diff --stat
git diff --cached --stat
```

记录工作树根目录、分支、完整提交号、未提交及未跟踪文件，以及实际受审对象：提交版本、工作区版本，或某一明确差异范围。**仅记录 HEAD 不能代表含未提交改动的工作区。** 受审的未提交文件要有可比较的差异摘要或文件哈希；不将敏感内容复制到报告。

明确纳入与排除的模块、服务器、平台、后端和管线。不要假定当前在主干，也不要为获取“干净基线”清空已有工作。

### 2. 按风险与业务链路分组

下面只是候选分组，不是已经批准的本轮计划；实际顺序按风险、改动范围和依赖决定。

| 候选分组 | 重点 | 专项技能 |
| --- | --- | --- |
| 协议与凭据 | 请求基址、鉴权、重定向、错误语义、凭据边界 | [Emby](../.claude/skills/momoka-emby-api/SKILL.md)、[Jellyfin](../.claude/skills/momoka-jellyfin-api/SKILL.md)、[飞牛](../.claude/skills/momoka-fnnas-media-api/SKILL.md)、[Plex](../.claude/skills/momoka-plex-api/SKILL.md) |
| 账号、来源与状态 | 登录切换、来源身份、权限、持久化、异步结果隔离 | [Shell](../.claude/skills/momoka-winui-shell/SKILL.md)及对应协议技能 |
| 播放生命周期 | 规划、起播、续播、上报、换源、换片、取消与释放 | [播放](../.claude/skills/momoka-playback/SKILL.md) |
| 输出与字幕设置 | 保存值与生效值、切换残留、设备回退、字幕选择和样式 | [视频](../.claude/skills/momoka-video-output/SKILL.md)、[音频](../.claude/skills/momoka-audio-output/SKILL.md)、[字幕](../.claude/skills/momoka-subtitles/SKILL.md)、[着色器](../.claude/skills/mpv-shader-quality/SKILL.md) |
| UI 与能力显隐 | Attach 生命周期、导航、绑定、权限、显隐与恢复 | [Shell](../.claude/skills/momoka-winui-shell/SKILL.md)；涉及集成时加 [MoviePilot](../.claude/skills/momoka-moviepilot/SKILL.md) |
| 测试与交付工具 | 回归覆盖、证据新鲜度、脚本失败路径、依赖与发布一致性 | [验证](../.claude/skills/momoka-verification/SKILL.md) |
| 跨模块复核 | 从用户入口追到实际效果，查各阶段遗漏的边界和交接 | 按所涉链路组合上述技能 |

服务器界面按产品分别检查，不把一种服务器的界面和能力当作通用实现；播放后端与播放管线分别列覆盖。能力或默认值以本次源码为准，不硬编码历史文件数、测试数或旧截图结论。

每个阶段写清：编号、目标、入口和文件范围、专项技能、前置依赖、检查方式、安全边界、完成条件、明确未覆盖项。

## 五、分阶段只读审查

每阶段按以下顺序执行：

1. **重读当前阶段规则与基线。** 确认没有并发写入，检查 HEAD、暂存区和未提交文件是否变化。
2. **追完整业务链路。** 结合调用者、状态来源、使用方、异常分支、取消和清理判断；不能只看一个方法或只扫 diff。
3. **检查现有测试。** 运行适用的安全离线检查时确认工具真实覆盖了目标；需要改测试、加临时插桩或进行有副作用的验证，先说明并取得相应授权。
4. **验证候选问题。** 核对触发条件是否可能发生、是否有上游约束、是否已有防护、用户是否真的受影响，并确认最小修复方向。
5. **保存问题与覆盖记录。** 区分已经检查、未检查和因环境或授权无法验证；无发现不等于证明没有缺陷。

问题至少包含：稳定编号、优先级、状态、基线、文件与准确行号及成员名、触发条件、实际影响、证据类型、最小修复方向、回归验收办法。行号可能随代码变化，不能只靠行号恢复结论。

### 问题状态与优先级

- 状态转换：候选经复核后记为“已确认”“待验证”或“排除”；只有已确认且获准修复的问题才进入“已修复待验收”，验收通过后记为“已验证”。基线变化使证据失效时记为“待复核”；排除项保留理由，不进入修复流程。延期或不修复的已确认问题另记理由与决定者，不伪装成已解决。
- 已确认要有可复核的源码因果链或复现证据；明确“静态证据、离线测试、隔离运行、真实服务器”中的实际证据类型与缺口。
- 优先级建议：P0 为需立即隔离的严重风险，P1 为严重功能或安全问题，P2 为一般功能缺陷，P3 为低影响的实际缺陷。按真实影响和触发条件定级，不按修改难度或个人喜好定级。
- 纯风格建议、非必要重构和未来假设单列为建议，不混入缺陷数量；测试缺口单独记录，只有支撑实际错误时才作为缺陷证据。

### 安全边界

遵守 [项目播放验证与凭据规则](../CLAUDE.md)。只读服务器访问仍可能登录并访问真实数据，不能称作离线验证；真实播放、观看记录上报、共享媒体或元数据修改等有副作用操作须有明确授权。

不读取真实明文令牌做断言，不把凭据写入报告、日志、URL 或命令；不改真实用户设置做验证。疑似严重风险及时报告，但报告风险不自动授权修改代码、删除数据或扩大测试范围。

## 六、阶段交接与上下文管理

### 1. 先有持久记录，再压缩

一轮审查可使用 `docs/代码审查-<主题>-<YYYY-MM-DD>.md` 保存总记录；内容较大时按阶段拆分并相互链接。已有报告先核对归属和内容，不覆盖其他任务的记录。本文不会自动创建某一轮审查报告。

阶段结束时依次执行：

1. 写入已覆盖范围、问题、证据缺口、关键取舍和下一阶段入口，记录当前代码基线。
2. 对新增或更新的记录完成文档内容、链接、命令与差异一致性检查，按项目规则提交本次记录；不夹带已有代码改动。
3. 当前执行环境有明确上下文压缩功能时再使用；不可用则如实记为“已保存交接，未执行系统压缩”。**保存摘要不等于系统上下文压缩，不能声称已经压缩。**
4. 向用户汇报本阶段结果、记录位置、压缩实际状态和下一阶段入口；持续执行时可用简短进度说明，不必结束当前响应。
5. 本阶段完成且下一只读阶段在既定范围内、前置条件满足时，按下方恢复步骤自动推进；用户要求暂停、出现安全风险或需要新的范围决定时停止。到达汇总复核出口后等待明确修复授权，不自行创建定时或后台续跑任务。

纯审查记录的提交不因此触发构建、探针或发布。上下文压缩不能代替阶段完成条件；自动推进与子代理只在本轮审查范围内执行，不扩大安全或修复授权。

### 2. 下一阶段的恢复步骤

自动推进或收到用户继续指令后：

- 读取现行规程、本轮审查记录和下一阶段专项技能，不依赖压缩后的记忆猜细节。
- 比较当前提交、暂存区、受审未提交文件及新增文件与已记录基线；不能只比较 HEAD。
- 代码发生变化时标记受影响结论“待复核”，确定并记录新的受审基线，保留原有证据来源。
- 确认本轮审查已明确启动、当前阶段完成且下一只读阶段在已确认计划内；满足条件即可自动进入，不逐阶段索取授权。未完成的阶段先收尾；单独编写本文不等于启动审查。汇总后的自动推进或“继续”不代替明确的修复授权。

## 七、汇总复核与分批修复

### 汇总复核

全部计划审查阶段结束后，仍先做只读汇总：

- 按根因去重，保留多个触发入口，避免同一个问题重复计数。
- 复核高优先级、证据不足、跨模块及基线已变化的问题；排除误报并保留简短理由。
- 将待验证项和测试覆盖缺口与已确认缺陷分开。
- 列出建议修复顺序、依赖、最小范围、验收办法，以及需要用户决定的产品行为或规则取舍。
- 报告候选修复清单后停止，等待用户明确批准；不以“全部审查已完成”为由自动开修。

### 分批修复

用户批准后，按相关问题形成小批次：

1. 再次核对问题在当前代码上仍成立，保护其他未提交工作。
2. 实施最小必要修复，不搭车重构，不修改规程来消除问题。
3. 编写或更新覆盖行为、边界和回归风险的相关测试，完成本次改动要求的编译与检查。
4. 按项目规则创建对应提交，只包含本次改动和相关测试，记录问题编号、提交及检查结果。
5. 每批完成后保存交接、报告剩余项并等待指令；完整批次验证安排遵守现行交付规则，不每个小修机械重复全量检查。

若用户要求提前处理严重问题，单独记录其授权范围、插入的修复批次和基线变化；恢复审查时复核受影响结论，不悄悄改变原计划。

## 八、最终验收与交付

修复结束后，对本轮最终代码完成 [现行交付验证](../CLAUDE.md) 与 [对应操作](开发与验证.md)，不复制固定测试数量或过时命令。

- 多类改动取适用验证要求的并集；必需检查失败、未执行或跳过，不能宣称交付完成。
- 测试与运行证据必须对应最终代码；之后改动覆盖路径，重跑受影响检查，不复用旧报告冒充新结果。
- UI 变化按要求取得运行和视觉证据；播放变化分别报告后端、管线与真实服务器覆盖，不用一种探针证明全部场景。
- 说明已修复、已验证、延期、不修复和仍待验证的问题，以及未审范围和风险；没有覆盖的范围不能宣称“整个项目无问题”。
- 审查完成、修复完成、验证通过、推送和发布是不同状态；上传和发布只按用户实际授权执行。
