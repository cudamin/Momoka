### R-014 [P2] 不可解码的非空图片缓存持续命中，冷却重试无法恢复

- 状态/基线：已确认；未修复。发现阶段 7，固定源码 `c34a5e545333ea4c9f12ca2573bc6034029ecc04`。

- 触发条件：同一图片身份、标签和宽度的 .img 文件非空但损坏，或一次 HTTP 200 非图片字节被写入缓存；之后服务器正常但缓存键未变。
- 预期行为：确认缓存内容是坏图时应有精确失效和重新获取的恢复路径，不能把再读同一坏文件当成有效重试。

- 证据类型：固定源码静态因果链；微软 SetSourceAsync 坏数据可抛异常文档（非 WinUI 运行）；未执行新增产品故障回归。

- 最小修复方向：明确格式或坏数据错误时精确失效缓存键，允许有界再取；区分低内存、取消、权限和传输错误，不把 UI 框架引入 Core 或全量清缓存。

### R-017 [P2] 未改动的带偏移发行日期可能在元数据保存时被重写

- 状态/基线：已确认；未修复。发现阶段 7，固定源码 `c34a5e545333ea4c9f12ca2573bc6034029ecc04`。

- 触发条件：Emby 原 PremiereDate 有时区偏移，日历日与 UTC 日不同；用户原样保存表单，或只改名称而不改日期。
- 预期行为：日期框未改变显示日历日期时，保留服务器原时间和偏移；只查看加保存不能产生意外日期改动。
- 静态因果链：
  1. Read.Date 按原 DateTimeOffset 日历日显示 yyyy-MM-dd，表单没有原偏移和时刻。
  2. Moment 用 AssumeUniversal 把同一天重建为 UTC 午夜，SetDate 却比较原 UtcDateTime.Date 与新值 UTC 日期。
  3. 2016-08-26T00:00:00+09:00 显示 2016-08-26，原 UTC 日是 2016-08-25，新 UTC 日是 2016-08-26，因此没改日期也被判 changed。
  4. SetDate 写成 2016-08-26T00:00:00.0000000Z，ApplyTo 返回 true，EditAsync 便 POST 整份元数据，而非无改动返回。
- 实际影响：未碰的发行时刻和偏移被抹掉，UTC 时刻可偏移或跨天，纯查看保存也可能变成共享元数据写入；本阶段未提交任何真实修改。

- 证据类型：固定源码静态因果链；固定 Emby 官方 SDK 4.10.2.0 字段/路由字典（非真实服务器）；相同 10.0.11 CoreLib DateTimeOffset 属性/解析观察（非产品执行）；未执行新增产品故障回归。

- 最小修复方向：按表单实际展示和修改的日历日判变化，未改时保留原值；明确真改日期的时区策略，不顺手重写其它日期。
