## 已确认缺陷

### R03-001 · P1 · 新账号登录失败会改写其他保存凭据的服务器绑定

- 位置：`src/Momoka.Shell/ViewModels/SignInViewModel.cs:470–485`，重点473–477；`src/Momoka.Core/Services/SettingsService.cs:94–113`。
- 触发：同URL原来属于已保存的服务器A，其中有账号a及保存令牌／密码；该URL现在属于服务器B。用户公开探测B，尝试新账号c，但认证失败。ResolveServer按URL拿到A的活配置；VM在认证前将整服ServerId／产品／URL改成B，失败或取消没有恢复原绑定。
- 后果：a的旧凭据仍在，普通退出App:325会保存已经改变的配置；下一次恢复以B作为预期身份，B的公开信息通过核对后，向B发送原属A的保存令牌，401还会触发保存密码回退。一次失败的新账号登录改变了其他账号的凭据边界。匿名夹具证实可发送，不表示真实凭据已经泄露。
- 证据：实际Shell VM与生成命令、真实Core Session／SettingsService／Store，只有HTTP和保护器是匿名替身。对照没有尝试c：ServerId保持A，恢复拒绝，旧令牌／密码请求均0；c失败后提示打开、ServerId变B，显式Save模拟正常关窗保存，LoadStrict重载仍为B，恢复a发出旧令牌1次、旧密码1次。请求体核对保存的占位密码，未输出其内容。最后恢复仍false，不能用登录未成功否定已经发送的凭据。见 `P/repro-results.json` 的 `failed-login-rebind` 和对照。
- 最小完整修正：复用含保存账号的配置前，拒绝已知服务器身份错配，保留原绑定和凭据，走明确删除旧配置后重新添加的现有用户流程；缺失新ID不得擦除已知ID；保留既有同身份合法产品／反代纠正。仅延后赋值、仅失败回滚都不完整，成功的c登录也不应把a的旧凭据一起重绑定。回归覆盖错误密码／取消／成功新账号与旧账号隔离、缺ID、同身份纠正和保存重载。
- 已由登录与会话审查者交叉核对，独立复核了实际反例。`ServersViewModel.TestAsync:505–510`已对只读探测设置同形保护，不能据该路径的旧测试推断登录入口安全。

### R03-002 · P2 · 多服务器管理入口忽略已经确认的非管理员权限

- 位置：`src/Momoka.Core/Services/ServerCapabilities.cs:163–165,194–204`；真实消费 `SettingsViewModel.cs:894–909,973–979`。
- 触发：保存令牌恢复的Emby连接管理员位为null，随后能力探测已在 `_sourcePermissions` 中存入false。Sources仍只读scope的连接权限，对Emby按未知权限允许管理，显式插件入口也沿用该读数。
- 后果：同一来源菜单已经知道不是管理员，设置来源仍宣称可以管理；多服分组显示无效管理项并发送插件请求。本地能力显隐和执行守卫不一致，不代表服务器越权成功。
- 证据：真实Core匿名来源A（Emby／null）+B（Jellyfin），探测后 `PermissionsFor=false`、`Sources.IsAdministrator=true`；实际Settings私有SourceRows返回23行，显式插件GET1次、结果1项。真实ReplaceClient确认false后的对照为管理false、插件0项、新增GET0。23行是方法结果，不是实屏控件。见 `P/repro-results.json:explicit-admin-permission`。
- 最小修正：显式管理来源也消费与当前UserStateOwner和PermissionRevision匹配的已确认权限，没有确认时再按产品回退；插件请求前后沿用同一判据。补保存令牌恢复／多服／降升权／旧回执的交叉测试。
