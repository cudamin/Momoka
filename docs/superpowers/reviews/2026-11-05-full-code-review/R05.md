## 已确认缺陷

### R05-001 · P2 · 飞牛默认版本时长被填给其它时长未知的版本

- 位置：`src/Momoka.Core/FnNas/FnNasMediaAdapter.cs:251–255`，联动 `src/Momoka.Core/Playback/PlaybackPlanner.cs:101–105,122`。
- 触发：条目原始时长为 0，`play/info` 没有时长；默认版本 A 有 120 秒，版本 B 时长未知。`Sources` 按文件／同 media_guid 的视频流计算，正确保持 B 未知；外层 GetItemAsync 先用 A 补详情时长，再将它填给全部未知版本。
- 后果：选择 B 时，其媒体信息、播放请求及 FnNasSelection 都得到 A 的 120 秒。`FnNasMediaAdapter.Models.cs:320` 生成错误的播放上报 duration；`PlaybackService.Reporting.cs:343–354` 还用请求时长判定 EOF 位置与提前停止的已看阈值。实际播放和服务器写入没有执行，不能声称已改变真实观看记录。
- 证据：`E/repro-final/repro-results.json` 的 `fnnas-version-duration` 执行实际 Core 的 Sources → EmbyClient.GetItemAsync → PlaybackPlanner → PlaybackRecord：raw B 为 null，后续均变成 120 秒；B 自己有 240 秒的对照始终保持 240 秒。每例只有 3 个匿名详情／流／进度请求。
- 最小完整修正：区分服务端给出的条目时长与默认版本推导的展示时长，避免后者回填其它版本；Planner 的飞牛分支也不得再用该展示时长替代未知源。保留原始条目时长可用时的既有约定，以及每版自身时长优先。只删适配器循环不完整，因为 Planner 仍有同样的回退。
- 覆盖缺口：现有多版本测试仍有原始条目／play-info 的 90 秒，未覆盖“条目未知、A 已知、B 未知”；补缺失／零／非有限时长和已知 B 对照。该发现由协议审查者与主代理分别复核，交 R10 沿原编号接续。

### R05-002 · P2 · Plex 已看写入成功后，补读失败会丢失确认并重发写入

- 位置：`src/Momoka.Core/Plex/PlexMediaAdapter.cs:277–280`；调用 `EmbySession.cs:526–540`、`ItemCommands.cs:591–610`、`DetailViewModel.cs:3790–3834`。
- 触发：scrobble/unscrobble 已成功，紧接的 metadata 读取失败。适配器将两次请求放在同一 Task；卡片只在整个 Task 成功后 Patch，详情也要等它完成才继续。
- 后果：补读 503 时，已经写入仍显示“标记失败”，卡片不确认目标位；补读 401 会触发 Session 重新认证并重跑整个委托，scrobble 被再次请求。这里确认的是重复请求及错误反馈，不推断真实 Plex 的重复计数或数据损失。
- 证据：`plex-write-readback` 经实际 Session.SignInAsync／Capture.ExecuteAsync／MarkPlayedAsync：正常为写 1、读 1；补读 503 为写 1、读 1且抛 EmbyApiException；首次补读 401 后同账号重新认证为写 2、读 2、登录 2。全部为占位身份与假传输。卡片／详情反馈由两名审查者独立跟踪源码，未声称执行了这个失败场景的真实 WinUI。
- 最小完整修正：复用飞牛现有的“先确认写入、后独立补读”语义。补读重认证只能重读；保留字段组顺序、来源／条目／页面寿命和“已保存，但刷新失败”的反馈。不能只吞补读异常，也不能伪造完整 UserData。
- 覆盖缺口：现有 PlexAffordance 成功路径断言两次请求，没有覆盖中间已确认而后读失败。交 R07，不与 R04 可选正文读取候选混号。

### R05-003 · P2 · Plex 下一集只查全服前 20 条，漏掉后页目标剧

- 位置：`src/Momoka.Core/Plex/PlexMediaAdapter.cs:255–262`；消费 `src/Momoka.Shell/ViewModels/ResumeSlot.cs:27–34,62–67`、`src/Momoka.Core/Emby/ResumeRow.cs:32–35`。
- 触发：GetNextUpAsync 指定某部剧、limit 为 1，但该剧在全服 On Deck 的第 21 条或之后。当前只读取一页 `max(limit,20)`，随后才按剧 ID 过滤，忽略 totalSize 和后续页。
- 后果：明明仍有下一集，却返回空；“继续观看”标已看后的替换流程按无下一集撤掉卡片。
- 证据：`plex-next-page` 用遵循本客户端分页头契约的匿名 21 条列表。目标在首条时返回 1，ResumeRow 保留替换；目标在第 21 条时只请求一页并返回 0，ResumeRow 返回 null；同一实际客户端 QueryResumeAsync(20,1) 能读到目标。没有运行真实 PMS 的 On Deck 排序或 WinUI 集合。

### R05-004 · P2 · Plex 码率单位未转换，媒体信息低 1000 倍

- 位置：`src/Momoka.Core/Plex/PlexMediaAdapter.Models.cs:220,256`；消费 `src/Momoka.Core/Emby/ItemDetail.cs:596,725–729,744`。
- 触发：Plex Media／Stream 返回 bitrate，例如 8000 kbps。官方前端仅解析整数，并给原值追加 kbps；本地直接写入共享 bit/s 字段。
- 后果：总码率 8000 进入共享格式化后成为 8 kb/s，应为 8 Mb/s；视频和音轨独立码率同样错误。
- 证据：固定官方 Desktop 4.163.0 JS 的 convertMediaItems、整数解析和媒体信息 formatter 已核；`plex-bitrate` 执行实际映射与 ItemDetail.MediaInfo，输入视频轨 7000 kbps，最终显示 `7 kb/s`。这是生产格式化输出，不是实屏截图。
- 最小修正：在 Plex 映射边界将媒体与轨道 kbps 换成 bit/s，保留缺值／非法值语义并处理乘法溢出。补真实单位对照，不能把测试期望继续固定为原始整数。显示消费交 R16，播放规划联 R10。

### R05-005 · P2 · Plex 整剧和整季已看状态未使用已看集数

- 位置：`src/Momoka.Core/Plex/PlexMediaAdapter.Models.cs:118–127`；消费 `EmbyItem.cs:964`、`ItemMenu.cs:301–309`、`CardItem.cs:639`、`DetailViewModel.cs:2777,3794–3802`。
- 触发：show／season 的 leafCount 与 viewedLeafCount 均为 2，未提供单片 viewCount。官方容器语义使用已看叶子数，本地一律按 viewCount > 0 设置 Played。
- 后果：已看完的剧／季显示未看，菜单缺少“标记未观看”，详情切换又发 scrobble，无法从当前状态走反向标未看。
- 证据：官方 JS 的 scrobble 成功回调按容器更新 viewedLeafCount，单片才更新 viewCount；其类型模块明确 show 和 season 都是容器。`plex-container-played` 执行实际 Item 与 ItemMenu.For：show／season 两例 Played=false、反向菜单=false；movie 的 viewCount=1 对照均为 true。两名审查者独立核对消费者，未运行真实 UI 或服务器状态更改。
- 最小修正：show／season 按有效 leafCount、viewedLeafCount 映射 Played 与未看集数，movie／episode 保持 viewCount。明确空容器、缺字段和部分已看边界；补完整映射→菜单／详情回读用例。交 R06／R07，和 R05-002 的写入确认问题是不同根因。
