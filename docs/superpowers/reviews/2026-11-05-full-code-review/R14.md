## 确认缺陷

### R14-001 · P2 · 删除缓存失败会恢复已经被服务拒绝的旧凭据

- 位置：`DandanPlayBuiltInCredentialSource.cs:65–71,93–104`；`DandanPlayClient.cs:186–193`；发送路径 `.Send.cs:59–63`。
- 触发：旧凭据缓存还在提前刷新时间之前，缓存文件可以读取但删除被文件共享限制或权限拒绝。GET收到401/403，Invalidate清内存、吞掉删除失败；下一次GetAsync又从同一文件恢复旧身份。
- 后果：唯一换钥重试继续使用旧签名，没有向凭据端点取新；服务能恢复时用户仍鉴权失败。POST“已清除缓存”的反馈也不成立，不应据此自动重发。
- 证据：完整真实Client/凭据源、Windows匿名缓存和允许读取但不共享删除的句柄：API2、端点0、两次签名均旧、文件仍存在。解除锁并再次Invalidate：端点1、当前Worker生成的AES-GCM信封被实际C#接受为新身份。无真实凭据、网络或部署。
- 最小完整修正：在现有实例内保留失效状态，成功取得新凭据前禁止重读被拒的旧盘缓存；新内存身份可继续用，即使新缓存落盘失败。保持现有串行闸门、取消和POST不重试。回归删除拒绝、写失败、401一次换新、POST结果未知及关停；跨进程不可写盘的持久失效仍需如实说明。

### R14-002 · P2 · 粘贴部分控制字符后独占输入无法再发送

- 位置：`DanmakuInput.lua:71–95,160`、`uosc/lib/utils.lua:795–799`；`MpvDanmaku.cs:62`、`MpvUi.cs:340`、`PlayerViewModel.DanmakuSend.cs:89–90`。
- 触发：Windows剪贴板带U+0080等C1字符。Lua只清C0/DEL，允许其进入草稿、建立pending并发通知；生产parser用char.IsControl拒整条消息，宿主不发失败回执。
- 后果：pending一直存在，用户删掉非法字符、换成有效文本也不能再次提交，须换库/换片重置。
- 证据：随包批准libmpv/Lua、实际uosc输入方法，假剪贴板/键盘：只发1条通知且payload带C1、合法context/requestId，编辑后pending和发送计数均不变；当前实际MpvDanmaku.ParseSend返回null。最终增强夹具50项通过，其中49原断言及1反例观察。没有真实剪贴板/窗口或跨进程事件联跑。
- 最小完整修正：统一两端Unicode清洗/校验；能关联合法context/requestId的非法内容给失败回执，释放pending并保留草稿。保留UTF-16上限和重复提交保护。回归C0/C1、emoji、粘贴、失败后修改/重试、旧回执及换片。
