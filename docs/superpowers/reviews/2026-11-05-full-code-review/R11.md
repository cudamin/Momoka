## 确认缺陷

### R11-001 · P2 · 起播首次UI发布使拖边暂停丢失恢复责任

- 位置：`src/Momoka.Shell/Views/PlayerPage.ClientRect.cs:559–617`，尤其604–608；`PlayerViewModel.Interaction.cs:12–17`；`PlayerViewModel.Events.cs:595–617`。
- 触发：集成模式首次启动，页面已经上台，Core活动handle已建立，尚在等待初始轨道时拖动窗口边沿。`BeginResizeFreeze`捕获尚无NowPlaying的UI交互context并发暂停；初始轨道完成后，实际NowPlaying通知推进UI generation/version并替换item。松手恢复把这笔仍属于同一活动handle的暂停责任判成旧交互，清标记后返回。
- 后果：默认开启“调整窗口后继续播放”也未发送恢复，用户需要手动恢复。页面拖边入口没有CoverUp门控；Core先公开active再等轨道，轨道读取走异步Task.Run，普通输入窗口可达。与R10-004/005准备失败的所有权不同。
- 证据：`managed-observations.json`两条resize观察。完整原样BeginResizeFreeze/FreezeForResizeAsync/ReleaseResizeFreezeAsync及CaptureInteraction/IsCurrentInteraction被提取编译，暂停端点和窗口为内存替身；同context命令为`[true,false]`，首次发布字段推进后为`[true]`且冻结责任被清除。发布字段变化依完整生产OnNowPlaying源流联证，临时宿主未执行完整Core→VM通知或WinUI拖边，不能称实机复现。
- 最小修正：冻结责任绑定被暂停的实际播放场次，允许跨首次UI发布，仍拒绝换片、停止和后继拖动。仅改用IsCurrentPlayback不完整，它仍包含会变化的UI generation/item。回归首次发布、普通拖边、原本暂停、关闭恢复设置、换片/停止和新拖动接手；同类窗口交接暂停也核首次发布边界。

### R11-003 · P2 · 合法固定长度include引用被当成错误文件路径

- 位置：`src/Momoka.Core/Mpv/MpvCustomConfig.cs:78–90`；准备异常55–56，实际起播`LibMpvBackend.cs:78`。
- 触发：内置独占启用自定义mpv.conf，文件含合法`include=%5%a.txt`且同目录有a.txt。mpv固定源码支持`%UTF-8字节长度%值`，本地副本预处理只认普通引号，直接找字面文件`%5%a.txt`。
- 后果：Prepare抛文件不存在，在原生创建之前阻断起播；普通include对照成功。用户配置入口和toggle→backend/custom刷新链已读。
- 证据：真实Core Prepare，匿名独立目录的plain通过、fixed失败，见`managed-observations.json`。固定mpv `options/parse_configfile.c:101–115`解析规则已读；独立批准哈希的真实libmpv仅create/load_config/destroy、不initialize，普通绝对include与固定长度绝对include均返回0，见`native-config-observations.json`。没有网络、媒体或用户配置扫描。原CustomConfig测试仅简单引用/嵌套，未覆盖该语法。
- 最小修正：include值按mpv语法解析固定长度引用，长度按UTF-8字节处理，保留尾注释、路径根、循环/深度和临时副本清理；不要自行重写其他普通mpv选项解析。回归ASCII、多字节、含#路径、普通引号和非法长度。
