### R04-001 · P1 · 多版本字幕验证的文件与协议写入目标不一致

- 位置：`src/Momoka.Core/Emby/ServerSubtitles.cs:19–24,60–67`，`src/Momoka.Core/Emby/EmbyClient.cs:1130–1132,1157–1166`；入口 `src/Momoka.Shell/Views/ItemCommands.Server.cs:463–476`。`EmbyItem.cs:1052` 的默认源是返回列表首项。
- 可达条件：Jellyfin 10.10.7 的一个主条目 A 带多个版本，A 为3D VideoFile、备选 B 为普通 VideoFile。官方 `BaseItem.GetMediaSources` 按 VideoFile、非3D优先排序，未优先所请求条目；`GetVersionInfo` 将每个源的 Id 和字幕流绑定到对应版本条目。因此第一源可以是 B。实际 Momoka 入口使用该默认源，没有手选版本的前提。
- 后果：对话框显示 B 的媒体文件和字幕，删除前 GET 也确认 B 的路径、完整轨道快照及索引；最终 DELETE 却发到 `/Videos/A/Subtitles/index`。官方 Jellyfin 控制器按路由 A 找条目，SubtitleManager 再按 A+index 查路径并删除。A、B有相同字幕索引时，会删 A 的字幕而保留用户确认的 B。搜索和下载也使用 A 路径；Jellyfin 不接收用于选择版本的 `MediaSourceId` 参数。
- 证据：`F/protocol-results.json:subtitle-target` 执行真实 Core 的 GetItem→DefaultMediaSource→ServerSubtitles→复读→DELETE。旧版合法输入顺序直接设为 `[B,A]`：复读2次，验证B后请求A，匿名模型中A删除、B保留。新版self-first输入 `[A,B]` 对照验证和请求均为A。**夹具未执行上游3D排序或服务器文件删除**；输入可达性及实际服务器删除含义分别由固定官方源码证明。协议审查者和HTTP审查者独立复核了这条链与反例。
- 版本边界：Jellyfin v12.4 的官方源码已新增所请求条目优先，收窄了当前UI的这个前件，不能说全部版本必现。不同路径仅分辨率较高并不足以推出B优先，官方宽度比较器对此返回0，故没有使用该前提。Emby官方SDK删除方法将 `MediaSourceId` 标为必填并发送，当前本地删除遗漏它；仅据SDK不能断言真实Emby会拒绝还是操作其他源。
- 最小完整修正：按产品绑定同一个已确认文件目标。Jellyfin将已验证媒体源解析到对应版本条目ID，搜索、下载、删除、读回均沿该目标；Emby删除携带已捕获的MediaSourceId。保留现有scope、路径、轨道快照与确认守卫；不能只增加B的检查而仍请求A。回归包括主/默认源不同、同索引不同字幕、来源丢失/更换、Jellyfin新旧排序和Emby源参数。
- 上游：[Jellyfin 10.10.7 BaseItem](https://github.com/jellyfin/jellyfin/blob/aefb9b2cffca3ccb7a95d89af0d9fb2040de6ed3/MediaBrowser.Controller/Entities/BaseItem.cs#L1057)、[Video版本来源](https://github.com/jellyfin/jellyfin/blob/aefb9b2cffca3ccb7a95d89af0d9fb2040de6ed3/MediaBrowser.Controller/Entities/Video.cs#L512)、[删除控制器](https://github.com/jellyfin/jellyfin/blob/aefb9b2cffca3ccb7a95d89af0d9fb2040de6ed3/Jellyfin.Api/Controllers/SubtitleController.cs#L91)、[实际删除](https://github.com/jellyfin/jellyfin/blob/aefb9b2cffca3ccb7a95d89af0d9fb2040de6ed3/MediaBrowser.Providers/Subtitles/SubtitleManager.cs#L351)、[v12.4源顺序](https://github.com/jellyfin/jellyfin/blob/83d0d0e7f76e23e2e085c8ff67d28b772d35967d/MediaBrowser.Controller/Entities/BaseItem.cs#L1205)、[Emby SDK](https://github.com/MediaBrowser/Emby.ApiClients/blob/f8499bd9d0e356b8a204a27b142765494dc6f450/Clients/Emby.ApiClient/Emby.ApiClient/Api/SubtitleServiceApi.cs#L52)。原文及SHA256存 E/upstream。

### R04-002 · P2 · 中文电脑名使 Emby/Jellyfin 请求在发送头部时失败

- 位置：`src/Momoka.Core/Emby/DeviceIdentity.cs:12–21,25–38`，`MediaServerKind.cs:44–54`，`EmbyHttp.cs:81–92,353–355`。
- 触发：Windows电脑名含中文等非ASCII字符；Create直接使用Environment.MachineName，Sanitize保留这些字符，随后进入鉴权头。生产SocketsHttpHandler没有配置头部编码选择器。
- 后果：默认HTTP/1.1传输写头部时拒绝非ASCII。匿名公开信息、登录和普通请求共用该设备头，连服务器测试也会报“无法连接（Unknown）”，而非有效请求。不是服务器密码错误。
- 证据：`F/repro-results.json:device-header` 在实际Core和默认SocketsHttpHandler上对两产品分别运行ASCII/中文设备名。ASCII均收到完整HTTP并成功解析JSON；中文均已接收TCP连接但未收到完整HTTP头，客户端抛EmbyUnreachableException。没有修改真实机器名，输入通过实际DeviceIdentity构造。运行时10.0.11；官方 v10.0.11 `HttpConnection.WriteString` 使用Ascii.FromUtf16并对InvalidData抛出，和v10.0.0原文一致。现有EmbyTests设备测试仅断言拼出的中文字符串，不能证明能发送。
- 最小修正：在统一设备头边界使用经服务端核实的编码或ASCII安全回退，保留稳定DeviceId及控制字符拒绝；REST、实时、播放头应保持一致。补真实回环传输对照，不能只改字符串期望。不把此处回环结果扩展成已验证真实Emby/Jellyfin或mpv。
- 上游：[.NET 10.0.11 HttpConnection](https://github.com/dotnet/runtime/blob/v10.0.11/src/libraries/System.Net.Http/src/System/Net/Http/SocketsHttpHandler/HttpConnection.cs#L502)，原文 `E/upstream/dotnet10-11-httpconnection.cs`。
