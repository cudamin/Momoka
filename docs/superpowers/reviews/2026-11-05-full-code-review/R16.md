## 已确认缺陷

### R16-001 · P2 · 亚克力零档仍绘制材料，回退时出现实底

**位置：** [ControlBackgroundBrushes.cs:69](../../../../src/Momoka.Shell/Views/ControlBackgroundBrushes.cs#L69)，69–79；设置说明 `UiSettings.ControlBackgroundOpacity`；详情操作、六个 EgPicker 与主页详情按钮消费。

**触发与后果：** 启用亚克力并把底色不透明度设为 0。代码先进入材料分支，`Opacity=1`、不透明主题 `FallbackColor`，只把 tint/luminosity 设为 0。零 tint 不会移除亚克力背景模糊和噪点；材质策略回退时画不透明回退色。因此“0 完全透明、没有底色”不成立。固定主树保留默认半透明的新增分支位于其后，不修复这个材料分支。

**证据与限制：** 本地完整方法、消费者和标准透明度测试已读/执行；测试只检查 tint 值，不能证明透明像素。微软稳定 `winui3/release/2.3.1`，提交 `a97562621a1d1ea397a38a3f512c9eef99db52d8` 的 `src/controls/dev/Materials/Acrylic/AcrylicBrush.cpp:494–548` 将背景叠到不透明回退层、应用模糊与噪点，656/668–672 实施回退；头文件 64–65 常量为 30 和 0.02。它与固定官方 main `cb1db78f713db99f3ff7c8d564aca3050f8ef0da` 两文件逐字一致，来源/hash 在验证 JSON。**未取得随包 WinUI 2.3.9 的精确源码 revision；没有实际合成器/屏幕像素。** 这里确认的是本地错误材料参数及官方实现语义，不是实测该机模糊半径或画面。

**最小修正与回归：** 零档常态在启用材料前走透明路径，保留既定悬停/按下反馈、画刷对象稳定性及主树“现有底色”默认半透明的授权行为。同步更正当前 `AppearanceOpacityTests` 与 DetailCustomization 探针的零 tint 断言。覆盖零→非零→100→零、Button/Toggle checked/Combo focused、主页详情、主题/材质切换及系统回退；真实纹理背景和回退截图另外核验。

### R16-002 · P2 · 坏轮播磁盘缓存不能自动恢复

**位置：** [BannerSlide.cs:197](../../../../src/Momoka.Shell/Views/BannerSlide.cs#L197)，197–204、327–333。

**触发与后果：** 相同图片 tag 的盘缓存损坏，而匿名服务器已经能返回有效图。底图仍走 `GetAsync` 后直接 WinRT 解码，绕过已有 `GetDecodedAsync` 的坏缓存重取。重建/Release 后继续读坏文件，`PictureUnavailable` 把仍有有效图片的影片从轮播摘掉。

**证据：** 完整生产 BannerSlide/BannerPictureLoader/HeroPictureLoader、实际 Core/store/WinRT 解码、匿名图片 handler，XAML BitmapImage 为读取 BMP 尺寸的边界。连续两次 Ensure：**0 GET、2 次缺图、坏文件保留**；只清除匿名缓存后同图 **1 GET 成功**。观察未执行真实轮播视觉删除，删除消费另由 HomeVM/HomeBanner 源码确认。

**最小修正与回归：** 底图字节及原像素解码经过已有 `GetDecodedAsync`，记原料/位图前继续检查 StillWanted、来源和清缓存代次。渲染阶段程序/资源失败不能当作坏原始图删盘。覆盖坏盘→有效重取、连续坏图、取消/源退出、Clear 期间迟到结果不回填；徽标可同机制核对，非必需徽标失败不能删有效幻灯片。

### R16-003 · P2 · 首选海报 404 后不尝试有效备用图

**位置：** [CardItem.cs:334](../../../../src/Momoka.Shell/Views/CardItem.cs#L334)，334–336、775、803–806、921–927；LibraryViewModel.CardImageTypes/NewCard 与 LibraryIndexCards.ImageTypes。

**触发与后果：** 首选和备用图都带标签，首选图片请求 404、备用仍有效。构造只保存第一种有标签的图，404 将整卡记为永久 `_missing`，没有继续图种候选。横幅/光盘/徽标/缩略图、飞牛横卡和播出平台图种消费受同根因影响。

**证据：** 实际 CardItem/store/HTTP，解码为受控字节边界。Thumb+Primary 两标签，Thumb 404，连续 Ensure **仅 1 次 Thumb 请求、卡片空图**；仅选 Primary 的对照 **请求 Primary 并成功**。没有真实 WinUI 海报像素或实服图种遗漏率。

**最小修正与回归：** 保留候选顺序及实际成功 ArtworkRef，以成功图建立内存缓存键。仅全候选明确缺图才永久记缺；5xx/坏图全部失败仍走冷却，取消/身份/权限/低内存继续原分类。不能把通用候选最终 null 全当永久缺图。覆盖首图404/坏图→备用成功、全部404、暂态失败、缓存重用和换宽取消；使用局部遍历即可。

### R16-004 · P2 · 拼图后续缓存命中重新占用已释放卡片的位图

**位置：** [CardItem.cs:156](../../../../src/Momoka.Shell/Views/CardItem.cs#L156)，151–173，联 ReleasePoster 879–899。

**触发与后果：** 第0格图片下载在飞，第1格已经内存缓存。当前容器换卡调用 Release(false) 清图并设 `_wanted=false`；第0格迟到后只进缓存，循环第1格却无条件 SetCollageTile，旧卡又持有位图。页面还保留 CardItem，LRU 淘汰不能释放它重新握住的图，破坏长滚动的资源释放边界。**未测真实进程峰值或实际卡顿。**

**证据：** Folder/CollectionFolder 两类匿名实际 CardItem/store 对照均为 wanted=false、tile0=false、tile1=true；各1请求。临时离树 keepWaiting=true 与旧容器放手四个对照均 wanted=true、两格正常显示；该问题不同于已修的旧 holder 误释放。

**最小修正与回归：** 缓存命中也按当前 `_wanted` 决定回填，继续保留下载进有界缓存及暂离树继续等待的语义。覆盖这六个对照、重回容器及换宽取消，缓存淘汰后确认离屏卡不持图；不通过取消整趟下载破坏现有回收契约。
