## 确认缺陷

### R10-001 · P2 · 同来源队列跨剧后沿用上一部剧的父信息

- 位置：`PlayerViewModel.Transport.cs:380,757`；父项采用在`306,319,340`，`PlayerViewModel.Events.cs:696–701`；消费在`PlaybackPlanner.cs:75–81`。
- 触发：显式播放队列由剧A走到同账号剧B。自动和手动下一项只比较来源Key，就把旧`_parent`传给B；非空父项使B跳过自己的父剧查询。跨到电影也不应继承剧父。
- 后果：画质分类和国漫已看阈值会使用A的类型/标签/发行公司。匿名A父项为“动画+Tencent”，B为真人剧，B自身无类型；自动EOF和手动Step得到的第二张实际ticket均带A父项，真实Planner判`IsDonghua=true`，正确B父项对照为false。没有实际改变服务器观看记录。
- 证据：`caller-results/observations.json`两条`cross-series-parent`；原样Start/Next/Step/NowPlaying方法和真实Core Planner，假播放端点。现有`UserQueueCases`虽有跨剧队列，只检查顺序，没有父项断言。
- 最小修正：只在下一项确属同来源、同剧时复用父项；跨剧解析新父，电影不继承剧父。回归自动/手动、同剧、跨剧、跨来源及剧→电影，不改变用户队列顺序。

### R10-002 · P2 · 换成其他条目或账号的版本后丢失用户队列位置

- 位置：`PlayerViewModel.Transport.cs:624–625`；`EpisodeNavigation.cs:16–20,51–53`；队列不补全的保护在`Transport.cs:520,659–669`。
- 同来源其他库版本可以有不同ItemId，跨来源版本也合法。换版时同来源原样传旧队列，新IdentityKey不在其中；跨来源传null，直接丢掉显式队列。随后手动下一项找不到当前位置，或自然EOF提前结束/退回目标剧默认全集。
- 证据：实际额外提取的完整`StartVersionAsync`调用既有完整Start，队列[A,C]切到同源A2时仍为[A,C]但当前A2无锚点；跨源A2时队列为空；同条目另一MediaSource对照仍正确下一项C。见`caller-results/observations.json`三条`version-queue`。版本发现合法入口及匹配由真实`MediaVersionDiscovery`和其同库/跨库测试源码联证；临时夹具预置已发现版本，没有重跑完整发现UI。
- 最小修正：显式队列保留当前位置和顺序，换版后的实际播放目标仍归原槽位；避免只按新身份反查，跨账号也不能清队列。回归目标版已经存在后续槽位的情况，防止重复身份导致定位到错误槽位。

### R10-006 · P2 · 起播轨道读取期间标记已看，会先上报停止再上报开始

- 最小修正：开始报告纳入同一场次顺序契约，在活动场次允许被手动补报使用前明确其开始队列位置/完成状态；不能仅在当前开始语句处晚拿锁。回归初始轨道等待、开始HTTP在飞、手动已看、开始失败及关闭排空。

### R10-007 · P2 · 快速暂停/恢复的位置读取完成乱序，发送旧暂停状态

- 位置：`PlaybackService.Reporting.cs:288–315`；外部调用`MpvProcessBackend.cs:240–256,292–297`，IPC异步续体在`MpvIpcClient.cs:248–263`。
- 暂停、恢复各自先异步读位置，再进入报告队列；同场generation不会区分先后事件。恢复读数先完成时发送unpause，旧暂停读数随后仍发送pause；周期更新前服务器接收到的最后状态与实际相反。
- 证据：真实服务在已监听状态下连续Pause(true/false)，两个受控位置读取先完成恢复再完成暂停；实际handle为未暂停，假HTTP顺序`unpause,false`→`pause,true`。见`service-observations.json`。外部IPC每条回复用独立异步TCS，续体没有顺序保证。未将ProgressChanged副作用扩大为已证实的UI故障。
- 最小修正：将位置读取与发送整体排序，或用单调事件序号在读后/排队/通知处拒绝过期结果。回归暂停→恢复→暂停、超时/取消、结束和正常周期更新；不用全局场次generation替代同场顺序。
