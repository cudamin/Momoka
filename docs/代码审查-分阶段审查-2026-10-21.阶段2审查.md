## 三、已确认问题

### R-001 [P1] 实时 WebSocket 跨源重定向保留 Emby 鉴权头

- **状态：已确认。** 发现阶段 2，代码基线 `c34a5e545333ea4c9f12ca2573bc6034029ecc04`。
- 文件/成员/准确行号：[EmbyRealtimeConnection.ListenOnceAsync](../src/Momoka.Core/Emby/EmbyRealtimeConnection.cs) **108～116 行**；`MediaServerHeaders.Create` **47～51 行**。
- 触发：已登录 Emby 的实时握手端点或反代返回可跟随的重定向，目标属于不同主机/端口/来源；不要求客户端把 token 写进 URL。
- 预期：认证仅属于最初受信任来源，跨源下一跳不获 Emby token/设备鉴权，或整个握手拒绝。
- 实际因果链：`CurrentConnection` → `Handshake` → 给默认 `ClientWebSocket` 设置 `X-Emby-Token` 与 `X-Emby-Authorization` → 调用无自定义 invoker 的 `ConnectAsync`。本机运行时的 `SetupInvoker` 新建 `SocketsHttpHandler`，**没有关闭 `AllowAutoRedirect`**；`HttpConnectionSettings` 默认 `_allowAutoRedirect=true`。`RedirectHandler` 只清标准 `Authorization`，再设置下一请求 URI 并发出；自定义 Emby 头仍在。其 `DisableAuth` 只改 `_sendStatus` 自动认证标记，不删除这些请求头。
- 可复核静态定位：运行时 `.ctor` 的 `IL_000F: ldc.i4.1`、`IL_0010: stfld _allowAutoRedirect`；跳转状态机的 `IL_0156: set_Authorization`、`IL_0222: set_RequestUri`、`IL_0364: SendAsync`；`SetupInvoker` 无 `set_AllowAutoRedirect`。完整选取 IL、DLL 版本和哈希在阶段证据 JSON。
- 影响：在上述运行时上，Emby 凭据能够随握手跳转离开原来源。**未证明真实 token 已泄露、未判 P0，也不将所有 Jellyfin/Plex/飞牛路径笼统列为受影响。** Jellyfin 的标准 Authorization 自动跳转另有不同清理语义，完整兼容留阶段 3。
- 已核对保护：REST 的 `EmbyHttpRedirect`、URL 不带 token、15 秒握手期限、scope 注销取消、每次重连取新 token 都不能阻止默认握手 handler 逐跳发出的自定义头。R-001 不等于 CAL-01 的旧文档描述，不重复计数。
- 未验证：未新增双回环重定向复现，没有真实 Emby 访问/ token 检查；未读取最终发布包的 runtime DLL。现有实际 101 握手、新 token 重连和退出断言都不涵盖 3xx。
- 最小修复方向：明确控制 WebSocket 握手传输，禁自动跳转或实施逐跳同源/凭据边界；保留重连和同步取消/异步释放，**不能回退 URL 查询令牌**。
- 回归验收：两个本地端口、占位身份下验证跨源拒绝/接收端零凭据；覆盖同源处理、跳数/降级、标准与自定义头、重连/取消，确认现有 101 和来源退出仍通过。需获修复/补回归授权再实现，不在本阶段插桩。

### R-002 [P2] 长下载错误正文无截止，堵住错误上报和队列

- **状态：已确认。** 发现阶段 2，同一固定代码基线。
- 文件/成员/准确行号：[EmbyHttp](../src/Momoka.Core/Emby/EmbyHttp.cs) `DownloadToFileAsync` **260～261 行**、`SendAsync` **391～396 行**、`ReadBodySafelyAsync` **440～445 行**；[实际下载调用者](../src/Momoka.Shell/Views/ItemCommands.Server.cs) `DownloadAsync` **267～275 行**、`SaveAsync` **360～361 行**。
- 触发：长下载收到 401/403/503 等非成功响应，错误体不足 8000 字节且一直不完成；来源/调用方没有取消。
- 预期：HTTP 状态已明确拒绝，应在有限时间内完成可选 drain 并上报原状态，释放响应与下载队列；合法成功长下载不套普通 30 秒总上限。
- 实际因果链：`DownloadToFileAsync` 直接用 `_long`（**106 行 InfiniteTimeSpan**）与原始取消 token 调 `SendAsync`，不经过普通 `SendAndReadAsync` 的 deadline。非成功时先 `await ReadBodySafelyAsync`，该方法 `ReadAtLeastAsync(8000)` 无独立期限，只能等够字节、EOF 或调用者取消；**之后**才 `Translate`/抛错误。已知拒绝仍可能无限等待。
- 影响：UI 的 `GuardAsync` 收不到失败，`DownloadGate` 等待未返回的 `SaveAsync`，同队列后续任务不前进。**来源退出/调用者取消仍可解除等待，不是无条件永久死锁**；失败时目标文件还未打开，不声称该路径已损坏目标。
- 已核对保护：handler 的连接期限只管建连；8000 是字节上限不是耗时上限；普通请求有 deadline，但长下载没有；part/长度/取消保护发生在成功正文之后，无法覆盖此前 await。成功长下载无限总时长是既定语义，本项不是要求把整段影片缩成 30 秒。
- 证据：源码因果链和真实 UI 命令/队列调用者。现有 `HttpDeadlineTests` 对**普通**错误体超时、长**成功**正文和取消，以及立即完成的 403/长度不符/旧文件保持，均已运行通过，但没有 `_long + 停住的错误体` 用例。
- 未验证：未新增暂停错误正文执行夹具，不访问真实服务器；不能用全套测试绿把缺失路径变成已覆盖。
- 最小修复方向：只为非成功响应的可选 drain 建独立短期限或不等待，超时仍保留 HTTP 错误分类、真正调用者取消仍是取消；不改变成功长下载语义。
- 回归验收：假传输的长下载 401/403/503 暂停正文应及时分类、响应释放/队列前进、不改旧目标或留 part；普通截止、成功长下载跨普通期限完成、调用者取消等既有回归不退化。
- 用户处理决定/修复提交：未授权、未修复。此为待汇总候选，不搭车处理。
