# Momoka WinUI 优化计划

制定日期：2026-11-14。

本文是新一轮优化的独立执行计划，范围为导航可靠性、设置交互、控件复用、依赖精简、列表性能及体验验收。当前状态为计划已制定，各阶段尚未实施；源码中发现的风险入口与已经复现的故障分别记录。

## 1. 目标与实施顺序

优先让操作和状态更可靠，再改善设置页的使用体验，最后依据测量结果精简依赖、优化性能。

| 阶段 | 优先级 | 工作 | 完成标志 |
| --- | --- | --- | --- |
| A | 高 | 导航取消、失败与异常时的状态一致性 | 页面、侧栏、面包屑和前进／返回历史保持一致 |
| B | 高 | 设置分组的键盘与读屏交互 | 展开状态可识别，折叠项退出键盘导航，焦点恢复正确 |
| C | 中 | 局部采用 SettingsCard | 三个代表性设置项通过布局、绑定、搜索和生命周期验收 |
| D | 中 | 核查并清理未使用依赖 | 依赖、资源和发布内容核对完成，体积变化有实际测量 |
| E | 中 | 按瓶颈优化列表和图片 | 固定场景下性能满足测量后确定的预算，资源增长受控 |
| F | 随各批执行，交付前汇总 | 联合体验验收 | 输入、布局、材质、通知及适用系统状态有明确结果 |

首批安排 A、B。C 的结果决定 SettingsControls 是否保留；D 中 Primitives 的只读核查可独立进行。E 可以先测基线，之后只处理已经定位的瓶颈。F 伴随各批收集证据，最终交付时按实际改动合并验证范围。

## 2. 阶段 A：导航状态一致性

### 现状与问题边界

[ShellPage.xaml.cs](../src/Momoka.Shell/Views/ShellPage.xaml.cs) 的 `Open` 在调用 `ContentFrame.Navigate` 前更新 `_current` 和历史，未检查导航返回值；`NavigationFailed` 当前主要负责停止动画。这是需要验证的状态风险入口，尚未通过实际失败或取消场景证明用户界面已经错乱。

### 实施步骤

1. 追踪普通导航、取消、失败、异常、返回和前进的完整事件顺序，覆盖当前页保留及页面初始化失败两种情况。
2. 先补能够触发风险的反例，记录页面、当前目的地、侧栏选择、面包屑及两方向历史在操作前后的状态。
3. 根据真实事件时序，让成功导航提交相应状态；取消或失败时保留或恢复与实际页面一致的状态。
4. 检查重复请求和迟到回调，防止上一笔失败覆盖下一笔成功导航。
5. 沿用现有页面归属和生命周期，不把纯 UI 导航改造成新的通用业务框架。

### 验收

- 成功、取消、失败、抛异常后，页面和导航展示状态一致。
- 失败后可重试，返回和前进次数、目标及顺序正确。
- 连续导航、账户或来源切换、详情返回时，没有旧回调覆盖当前状态。
- 在现有 [NavigationStateTests](../tests/Momoka.NavigationStateTests/Momoka.NavigationStateTests.csproj) 基础上补行为测试，并以真实 Frame 场景核对事件时序。

## 3. 阶段 B：设置分组的键盘与读屏交互

### 现状与问题边界

[SettingsPage.xaml](../src/Momoka.Shell/Views/SettingsPage.xaml) 的分组标题使用普通 Button、名称和箭头；[SettingsPage.xaml.cs](../src/Momoka.Shell/Views/SettingsPage.xaml.cs) 的 `ApplyCategoryItemHeights` 主要通过 `MinHeight` 控制折叠，Tab 状态没有同步跟随展开状态。实际是否出现不可见焦点、读屏是否正确播报，仍需运行验证。

### 实施步骤

1. 在多服务器分组场景记录 UI Automation 的名称、角色、展开状态和实际 Tab／方向键序列。
2. 对照 WinUI Gallery 的 Expander 实现，评估它与当前分组 ListView 的选择、虚拟化、滚动及搜索定位能否配合。
3. 原生 Expander 可等价适配时，采用其展开语义和输入行为；若需要大幅重排列表，则记录原因，评估最小的状态 peer 与焦点修正。
4. 折叠时将焦点安置到可见的合理位置，使隐藏条目退出键盘导航；展开后保留预期的选择和焦点恢复。
5. 覆盖动态新增／移除服务器、当前分类自动展开、窗口隐藏重开和搜索跳转。

### 验收

- 读屏可辨认分组名称及展开／折叠状态。
- 折叠内容没有空白焦点，后续分组标题仍正常生成并可达。
- 当前设置页、未保存草稿、类别滚动及展开偏好正确保留。
- 通过 [SettingsPageStateTests](../tests/Momoka.Tests/SettingsPageStateTests.cs) 等相关行为检查，并补真实键盘、UIA 和读屏证据。

## 4. 阶段 C：局部采用 SettingsCard

### 首批范围

从 [SettingsViewModel.cs](../src/Momoka.Shell/ViewModels/SettingsViewModel.cs) 的“界面”设置选取三个代表项：UI 动画、每页条目数、隐藏功能下方说明。它们分别覆盖开关、数值编辑及说明显隐。当前 SettingsControls 已声明依赖，首批可基于现有版本评估。

### 实施步骤

1. 读取当前包对应的 SettingsCard 源码、模板、AutomationPeer 和样例，核对实际可用的属性及响应式状态。
2. 给首批条目建立有限的模板选择范围，避免修改一个全局 Toggle／Number 模板就迁移全部设置。
3. 保留标题、说明、双向绑定、实际输入控件名称、搜索定位和既有保存语义。
4. 根据共享卡片背景调整容器，避免整张卡片里重复叠加独立卡面和边框。
5. 比较改前、改后的布局复杂度与实际体验；确认有收益后，再列适合扩展的设置项。

### 验收

- 宽、中、窄窗口及长文本下，标题、说明和操作区不遮挡，内容正确折行。
- 数值范围、无效输入、保存失败、重置和说明显隐行为正确。
- 搜索能定位并聚焦实际控件，窗口隐藏重开后草稿和滚动位置保留。
- 键盘及读屏名称正确，普通设置卡不会多出无意义的 Tab 停靠点。
- 复用 [SettingsControlNameTests](../tests/Momoka.PageContractTests/SettingsControlNameTests.cs) 和设置状态测试，补代表性运行与画面检查。

SettingsExpander 留到确有分组收益时单独评估。引入折叠会影响搜索展开、焦点恢复和状态保存，不能只替换容器。

## 5. 阶段 D：依赖核查与精简

### 核查范围

[Momoka.Shell.csproj](../src/Momoka.Shell/Momoka.Shell.csproj) 当前声明 CommunityToolkit.Mvvm 8.4.2，以及 Animations、Segmented、Primitives、SettingsControls 8.2.251219。前两类 WinUI 扩展和 MVVM 有实际调用；Primitives、SettingsControls 尚未找到对应控件使用。实施时重新检查源码、传递依赖和资源引用，以届时依赖图为准。

### 实施步骤

1. 建立“直接引用、实际类型／资源使用、传递依赖、发布资产”的对应表。
2. 优先评估 Primitives 的删除；根据阶段 C 的结果决定 SettingsControls 的保留或移除。
3. 对候选进行独立依赖改动，重新还原并核对构建目标、资源合并和运行依赖。
4. 使用相同发布配置比较文件清单、合并 PRI、ZIP、冷启动及设置页面加载。
5. 按测量结果记录收益与代价；共享传递依赖仍被其他包使用时，不能将其体积算作本次节省。

### 验收

- 动画、分段选项、设置及应用启动没有资源或类型缺失。
- Windows App SDK 拆分策略和用于满足 Toolkit 依赖的占位引用经过核对。
- 报告包含实际文件／字节变化，尚未测量时不填写预计节省值。
- 依赖验证与交付时机遵循 [CLAUDE.md](../CLAUDE.md)；依赖升级与其他优化分批处理。

## 6. 阶段 E：列表与图片性能

### 测量范围

优先媒体墙、长集列表和首页货架。音乐现有的有限视口、图片需求与回收机制可作为参考；是否适合其他页面，要由相同场景测量和生命周期分析确定。

### 实施步骤

1. 准备固定匿名数据和本地图片，按适用页面建立 100、1,000、10,000 条数据集，分别测冷缓存与热缓存。
2. 记录首个有效内容呈现时间、固定滚动过程的帧时间、实际生成控件数、图片请求／需求数，以及多次进出后的保留资源。
3. 区分网络等待、图片解码、集合重建、布局和订阅未释放，先确定主因和数值预算。
4. 每批只调整已经定位的瓶颈，比较相同环境、相同数据和相同操作下的结果。
5. 检查分页追加、排序、筛选、删除、缺图、加载失败和迟到响应，防止优化影响末项可达性或数据正确性。

### 验收

- 实际生成控件数与视口及缓存策略相符，不随数据总量失控增长。
- 页面往返后的图片需求、订阅和保留资源回到确定的预算范围。
- 分页末项可达，返回后滚动锚点与焦点正确，旧响应不能写入新页面。
- 优化报告同时给出基线、结果和环境；没有显存或功耗测量时，不推导相应收益。

## 7. 阶段 F：联合体验验收

本阶段随每批改动选择相关项目，交付前汇总。测试目标与实际覆盖分别记录，当前没有运行证据的项目保持待验。

| 范围 | 重点场景 | 通过标准 |
| --- | --- | --- |
| 标题搜索与侧栏 | 输入法回车、防抖、物理 Ctrl+F、侧栏调宽、隐藏与恢复 | 输入不丢失、不重复提交，焦点始终属于当前有效控件 |
| 导航与命令栏 | 返回／前进、窄窗溢出、Enter、Escape、点外关闭 | 操作可达，逐层取消与焦点返回正确，没有误触发 |
| 布局与缩放 | 宽／中／窄窗、短窗、断点前后 1 DIP、跨屏 | 关键内容完整可见，末项可达，标题栏命中正确 |
| 文字与无障碍 | 文字放大、长文本、键盘、UIA、Narrator | 名称、角色、状态和焦点可识别，隐藏项不可导航 |
| 材质与主题 | 存活主题、高对比度、关闭透明、失焦与恢复 | 文本及焦点可读，回退正确，没有旧背景残留 |
| 动效 | 快速重复操作、打断、离页、系统／应用关闭动画 | 状态即时正确落定，失效目标有正常回退 |
| Windows 通知 | 已有失败通知的实际显示、关闭与注册生命周期 | 当前产品通知场景工作正常，失败可追溯 |

缩放目标为 100%、125%、150%、200%，文字大小目标为 100%、200%；按可用设备记录真实覆盖，计算夹具不能代替跨屏实测。[SystemNotification.cs](../src/Momoka.Shell/Platform/SystemNotification.cs) 已接入 Windows 通知，下一步是补实际弹显及相关环境验证。

## 8. 实施约束与阶段交付

- MVVM 沿用现有 CommunityToolkit.Mvvm 和页面生命周期机制。针对取消、重新提交、切换账户、迟到结果及旧 finally 的忙碌状态归属补测试，有复现问题再最小修复。
- 保留现有主题范围、弹窗点外取消、按服务区分影视库、统一音乐库以及搜索来源栏的显隐约定。
- 官方实现优先，采用前读取固定版本源码及相关 helper／模板；兼容性不明确时先验证，不能随示例自动引入实验依赖。
- 窗口宿主迁移、浅色主题、MSIX 和新通知场景属于独立产品决定，不由本文自动批准。
- 实现直接进入实际页面；只有用户要求时才先做 Demo。每批完成相应测试与验证后提交、合并，并登记交付所需检查。
- 桌面运行验证串行执行。匿名数据和本地素材优先；真实服务器播放或有副作用的验证按项目授权范围执行。输入图片达到 40 张时暂停。
- 用户要求交付时，在最终主树汇总适用检查，通过后刷新发布件和快捷方式。此次文档生成只做文档内容、链接、编码与差异检查。

每阶段记录：源码版本、实际修改、测试结果、运行证据、未覆盖环境、保留问题、合并状态及是否已交付。遵循 [开发与验证](开发与验证.md) 的命令和 [WinUI 验证矩阵](../.claude/skills/momoka-verification/references/winui-validation.md) 的证据边界。
