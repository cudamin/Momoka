## 1. 产品与技术栈

Momoka 是第三方媒体库桌面客户端：用户自己搭 Emby、Jellyfin、飞牛影视或 Plex 服务器，本程序负责浏览、播放和管理。

| 项 | 取值 | 依据 |
| --- | --- | --- |
| 语言与运行时 | C# / .NET 10 | `global.json`、各 `csproj` |
| UI 框架 | WinUI 3（Windows App SDK） | `src/Momoka.Shell/Momoka.Shell.csproj` |
| 应用工程 | 非打包（`WindowsPackageType=None`）、仅 x64 | 同上；发布配置见第 12 节 |
| 播放内核 | libmpv（随包 `libmpv-2.dll`，不入库） | `src/Momoka.Core/Playback`、`src/Momoka.Core/Mpv` |
| 分发 | GitHub Releases 安装包；Microsoft Store 商店包 | `tools/publish.ps1`、`tools/installer.ps1` |
| 许可 | 本程序 GPL-3.0-or-later，附微软组件有限附加许可；随包 libmpv 保持 LGPL | [LICENSE](../LICENSE)、[THIRD-PARTY-NOTICES](../THIRD-PARTY-NOTICES.md) |

四套服务的实现差异见第 6 节，功能与实测范围集中见[后端能力矩阵](后端能力矩阵.md)。

## 2. 仓库结构

```
src/Momoka.Core      与 UI 框架无关的领域层：协议、设置、播放决策、纯规则
src/Momoka.Shell     唯一的桌面应用：WinUI 外壳、页面、视图模型、探针、自检
tests/               一个主测试宿主 + 数十个专项测试工程（见第 11 节）
tools/               构建、发布、质量、验证与回归入口脚本
assets/              随包资源：mpv 运行时载荷、mpv-ui（uosc 与 Lua 脚本）、着色器
docs/                功能文档、命令手册、交付台账与本文
.claude/skills/      按任务读取的项目技能（协议、播放、界面、验证等）
```

### 2.1 分层

- **`Momoka.Core` 不依赖 UI 框架。** 主测试宿主是普通控制台程序，可直接加载 Core。HTTP、持久化、播放决策、字幕/轨道规则、主题色推导都在这里。
- **`Momoka.Shell` 是唯一 `WinExe`。** 它持有 WinUI 视觉树、依赖注入容器、窗口与原生互操作，也放得下纯 UI 行为（code-behind）。
- **方向是 `View → ViewModel → Service → 外部世界`**，但不要求每个文件都走完整链路：纯展示判断就近留在页面，可复用的业务规则做成 Core 里的纯函数并配测试。

### 2.2 两个容易记错的位置

- `ActivationListener` 在 `src/Momoka.Shell/ActivationListener.cs`（无 UI 依赖，被主测试编译链接），不是历史路径 `Shell/ActivationListener.cs`。
- 依赖注册只有一处：`src/Momoka.Shell/Composition/ShellServices.cs`。找「谁创建了谁」先看它。

## 3. 启动与进程模型

入口是 `src/Momoka.Shell/Program.cs`，`Main` 手写（`DISABLE_XAML_GENERATED_MAIN`）：普通启动在创建 XAML 前准备数据目录、检查单实例并初始化日志；自检和探针的分流见下文。

### 3.1 启动顺序

1. **解析命令行**（`src/Momoka.Core/Infrastructure/StartupArgs.cs` 的 `Has` / `Text` / `Number`）。
2. **按入口分流**：自检用 `SelfCheckRun.Create` 建独立运行目录，严格读取设置副本；独立探针使用本次运行的数据目录。两者提前分流，不走普通启动的数据迁移和单实例交接。
3. **普通启动准备数据**：`SettingsStore.PrepareStartupData(AppPaths.PriorRoots)` 按需迁移旧产品目录；失败不阻止启动。
4. **普通启动交接实例**：先检查旧产品名的实例，再用命名 `Mutex` 判定当前实例；已有实例时发激活信号后退出，不另建窗口。
5. **进入应用**：正常启动的 `Run` 初始化日志与异常处理，再由 `Application.Start` 创建 `App`，随后进入 `OnLaunched`。

`App` 构造函数在普通启动与自检时先用 `ShellServices.Build` 组装依赖，读取界面语言并初始化本地化，再调用 `InitializeComponent` 加载 XAML；匿名探针不创建生产容器或读取已保存账号。`App.OnLaunched` 按入口分派探针，普通启动与自检则继续应用主题、把 `ShellPage` 放进 `HostWindow` 并恢复窗口位置。自检会额外安排检查；浏览外壳的启动流程仍会运行。工具运行与自检不检查更新。

### 3.2 窗口

- **主窗口不是框架 `Window`**：`src/Momoka.Shell/Windowing/HostWindow.cs` 用 `CreateWindowEx` 建 HWND，再挂 `DesktopWindowXamlSource` 岛。标题栏那 48 像素是自绘的，非客户区（系统三颗键）由 DWM 参与，所以拖拽、最大化、DPI 都要按 HWND 处理。
- **设置窗口是框架 `Window`**（`src/Momoka.Shell/Views/SettingsWindow.cs`），它的画布、标题栏和系统观察单独一套。
- **集成管线的视频画面**由 `src/Momoka.Shell/Windowing/CompositionVideoTarget.cs` 用 `SpriteVisual` + D3D11 合成交换链接进 XAML 视觉树。
- **`PlayerPage` 是外壳的兄弟 `UserControl`，不在 `ContentFrame` 里**。这是刻意的：播放层要盖住整窗、自己管标题栏与拖拽；导航栈里没有它。

### 3.3 日志与异常

`Log` 是静态入口，正常启动写文件（`logs/`）并保留最近 1000 行在内存里给诊断页。未处理异常分两路：`AppDomain.UnhandledException` 记错误，`TaskScheduler.UnobservedTaskException` 记警告后 `SetObserved()`（图片与播放都有没人 await 的长任务，不让终结器线程掀掉进程）。

### 3.4 命令行开关

`StartupOptions` 区分普通启动、工具启动、自检和探针。进入工具模式后不会注册系统通知或检查更新；`--play` 会真实起播，运行前须按[播放验证规则](../CLAUDE.md#播放相关改动的验证三档)选好数据与服务器边界。是否使用隔离数据目录由实际运行入口决定。开关及组合见[开发与验证「命令行开关」](开发与验证.md#命令行开关)。

## 4. 组合根与依赖

`ShellServices.Build` 建 `ServiceProvider`，开 `ValidateOnBuild` 与 `ValidateScopes`：漏注册的依赖在启动时就报错并点名，而不是等到某个页面第一次用到时变成空引用。容器必须在 UI 线程上建，`IUiDispatcher` 在那一刻捕获 `DispatcherQueue`。

容器里的东西几乎都是单例，按职责分四组：

| 组 | 关键对象 | 说明 |
| --- | --- | --- |
| 地基 | `AppPaths`、`ISecretProtector`、`SettingsStore`、`AppSettings`、`SettingsService` | 设置只加载一次、原地编辑；两个实例会让一页的修改在另一页看不见 |
| 服务端 | `EmbySession`、`CredentialVault`、`DeviceIdentity`、`EmbyImageStore`、`ServerCapabilities` | 会话按「服务器账号」分来源，缓存有磁盘预算 |
| 播放 | `PlaybackService`、`PlaybackPlanner`、`PlaybackBackendFactory`、`AudioDeviceCatalogue`、`ShaderGroupResolver` | 服务负责播放决策、后端选择和会话生命周期 |
| 界面 | `ShellPage`、`IShellActions`、`PlayerViewModel`、`MusicPlaybackViewModel`、`PlayerToolsController` | `ShellPage` 同时注册为 `IShellActions`，保证外壳动作不会指向另一棵隐藏视觉树 |

视频和音乐的播放状态由容器持有的 `PlayerViewModel` 和 `MusicPlaybackViewModel` 管理，用户翻库时播放能继续。普通页面默认自建视图模型，通过 `Attach(...)` 接收服务与身份。

`PlaybackService` 通过工厂取得后端；需要新开句柄时按设置选择内置 libmpv 或外部 `mpv.exe`。

## 5. 设置与本地数据

### 5.1 数据目录

`AppPaths` 集中确定设置、缓存、日志、截图和 WebView2 的落点，普通运行默认使用 `%LOCALAPPDATA%\Momoka`。普通启动用 `PriorRoots` 迁移旧产品目录；自检用 `ResolveProfile` 定位现有设置并复制到独立运行目录。具体路径见[开发与验证「数据与路径」](开发与验证.md#数据与路径)。

### 5.2 设置文档

`src/Momoka.Core/Configuration/AppSettings.cs` 一个类装下全部设置，顶层分区：

`Servers`（服务器与账号）、`Mpv`（后端、管线、自定义配置）、`Playback`（报告、续播、阈值、轨道偏好、字幕模式）、`Video`（输出、HDR、着色器档位）、`Audio`、`Shaders`、`Ui`（主题、字号、缓存预算、主页行）、`Trailer`、`Shortcuts`、`Danmaku`、`SubtitleTranslation`、`PlayerTools`、`MoviePilot`、`LocalMedia`。

几条与实现绑定的规则：

- **`SchemaVersion` + `SettingsMigration.Normalize`**：读旧文件时补齐缺省、清掉退役字段、把越界值夹回合法范围。旧字段被默认序列化选项忽略，下次保存自然消失——不需要写删除逻辑。
- **保存是原子的**：`SettingsStore` 写临时文件再替换，`SettingsSaveQueue` 把连续修改合并成一次落盘；设置页的「延迟保存」走 `ISettingsService`，由 UI 队列调度。

### 5.3 凭据

`ISecretProtector` 是客户端持久化凭据的加解密接口；`CredentialVault` 管理媒体账号档案，MoviePilot 和弹幕各有自己的存储入口。凭据处理规则见 [CLAUDE「凭据」](../CLAUDE.md#凭据)，播放器如何与媒体服务器凭据隔离见第 7.3 节。

## 6. 服务器协议层

### 6.1 共享传输

`src/Momoka.Core/Emby/EmbyHttp.cs` 是媒体服务器 REST 请求的公共传输入口之一，负责逐请求认证、超时、重定向、错误翻译和下载。它不修改共享的 `DefaultRequestHeaders`，避免并发请求串用身份；调用方根据异常类型区分连接、认证和服务端错误。各服务可有自己的传输实现。

`EmbyServerAddress.Normalize` 只在一处归一基址；`EmbyUrl` 里的相对路径因此不带产品前缀。把 id 拼进路径前要过守卫（拒绝 `.`、`..` 和含 `/ \ ? #` 的段），再转义。

### 6.2 四套服务的差异

| 关注点 | Emby | Jellyfin | 飞牛影视 | Plex |
| --- | --- | --- | --- | --- |
| 基址 | 归一化时补齐 `/emby/` | 保留配置的根或反代子路径 | 独立端点与签名 | 服务器直连 + plex.tv 账号 |
| 认证 | `X-Emby-Authorization` + `X-Emby-Token` | `Authorization: MediaBrowser`（令牌是同一头的属性） | 登录换令牌 + 请求签名 | `X-Plex-Token` |
| 用户作用域 | 路径带 `{userId}` | 令牌决定，需要时使用 query | 自有模型 | 自有模型 |
| 实时通知 | `/emby/embywebsocket` | `/socket`（另有应用层 `ForceKeepAlive`） | 任务轮询（`FnNasTaskWatch`） | `PlexRealtimeProtocol` |
| 片头片尾 | 章节上的 `MarkerType` | 10.10+ `GET /MediaSegments/{itemId}` | 使用播放器章节回退 | 详情请求带 `includeMarkers=1` |

协议细节与路由对照见各服务技能：[Emby](../.claude/skills/momoka-emby-api/SKILL.md)、[Jellyfin](../.claude/skills/momoka-jellyfin-api/SKILL.md)、[飞牛影视](../.claude/skills/momoka-fnnas-media-api/SKILL.md)、[Plex](../.claude/skills/momoka-plex-api/SKILL.md)。功能与验证状态见[后端能力矩阵](后端能力矩阵.md)。

### 6.3 会话、多账号与能力

- `EmbySession` 持有所有在线来源；每个来源一个 `EmbySessionScope`，固定「哪台服务器、哪个账号」。换默认管理账号不影响已捕获的作用域，退出该账号才撤销。
- 发起请求时通过作用域取该身份的最新令牌，而不是拿一份过期快照。作用域的生命周期参与播放的准入与撤销：身份被撤销要能把准备中的播放停掉，且只停一次。
- 聚合模式下，主页与搜索按来源聚合；交互和配置见[多服务器与多账号](多服务器与多账号.md)。
- `ServerCapabilities` 和 `ServerAccess` 分别汇总服务能力与访问权限。管理员标记未知时的处理因后端和操作而异，应使用相应能力判断。
- 页面的媒体请求由视图模型捕获当前的 `EmbySessionScope`，经 `EmbyClient` 分发给后端适配器和对应传输层。响应回来后还要比对作用域与页面代，身份已换或页面已离开就丢弃旧结果。

### 6.4 实时刷新

Emby、Jellyfin、Plex 复用 `EmbyRealtimeConnection` 并按各自协议解析通知。主页只用媒体库变化通知启动数据比对；飞牛的任务轮询是另一条链路。通知、重连与验证边界见[媒体库实时更新](媒体库实时更新.md)。

## 7. 播放

一次播放从当前条目和服务器账号出发，经 Core 决定如何播放，再交给播放器后端呈现。媒体请求、界面状态和服务器进度报告各有自己的负责人。

### 7.1 一次播放经过哪些模块

1. `PlayerViewModel` 把条目、版本和来源交给 `PlaybackService`。服务通过捕获的账号作用域取得服务器连接，并把播放条目交给 planner。
2. `PlaybackPlanner` 生成 `PlaybackRequest`，集中决定媒体地址、轨道、输出和续播位置；这部分可以脱离窗口与播放器进程测试。
3. `PlaybackService` 在允许同窗切换时复用句柄，否则通过 `PlaybackBackendFactory` 创建后端。`LibMpvBackend` 在进程内加载 `libmpv-2.dll`；`MpvProcessBackend` 通过命名管道控制用户的 `mpv.exe`。
4. `IPlaybackHandle` 将控制和状态回读交还上层。`PlaybackService` 管理起播、换片与停止，并经相应的服务器适配层报告进度。

### 7.2 两条呈现管线

内置后端有两种画面呈现方式，设置里叫「视频管线」：

| 管线 | 画面 | 控件 |
| --- | --- | --- |
| 集成（Integrated） | D3D11 合成交换链接进主窗 XAML | Momoka 自己的播放层 `PlayerPage` |
| 独占（Standalone） | mpv 自建顶层窗口 | 随包 uosc（`assets/mpv-ui`） |

`LibMpvPipelinePolicy` 在生成播放请求后落实内置管线需要的渲染和输入选项。具体选项以及自定义 `mpv.conf` 的适用范围见[播放技能](../.claude/skills/momoka-playback/SKILL.md)。

### 7.3 播放传输与凭据

`PlaybackHttpTransport` 在 .NET 侧持有媒体服务器认证头，并把受保护的资源映射成本机匿名回环地址。内置与外部 mpv 都只看到映射后的地址。重定向、播放列表限制和外部进程交接见[播放技能](../.claude/skills/momoka-playback/SKILL.md)。

### 7.4 会话与播放界面

`PlaybackService.Lifecycle` 区分准备中的请求和正在运行的句柄；同窗换片时使用播放代数丢弃旧回调。集成模式下，`PlayerPage` 呈现 `PlayerViewModel` 的状态，例如队列、时间轴和轨道菜单。输入和菜单要归属于当前尝试，换片后不能作用到另一项媒体。换集、报告、轨道和章节的细节见[播放技能](../.claude/skills/momoka-playback/SKILL.md)，菜单入口见[播放菜单与工具](播放菜单与工具.md)。

输出选项由 `MpvOutputOptions`、`MpvBaseline` 和 `ShaderGroupResolver` 等模块组装，规则分别见[音频输出](../.claude/skills/momoka-audio-output/SKILL.md)、[视频输出](../.claude/skills/momoka-video-output/SKILL.md)和[着色器](../.claude/skills/mpv-shader-quality/SKILL.md)。

## 9. 界面体系

### 9.1 外壳

`ShellPage` 承载自绘标题栏、`ContentHost` 画布和 `ContentFrame` 导航栈。登录卡与浏览容器并列，切换登录状态时两者共用同一个窗口、主题根和 `XamlRoot`。

两种外壳形态由 `UiSettings.EnableImmersive` 决定：

- **侧栏**：`NavigationView` 承载主要导航，页面给侧栏留出空间。
- **沉浸**：标题栏叠在页面之上，页面从窗口左侧开始布局。

`ReportTitleBarHoles` 把标题栏中的交互控件从原生拖拽区域排除。

### 9.2 页面与视图模型

会话相关页面通过 `ISessionScopedPage` 接收外壳的身份切换通知。页面拥有自己的异步操作和订阅，离开时取消或释放。视图模型创建方式见第 4 节，分页、会话切换和页面重进见[页面寿命参考](../.claude/skills/momoka-winui-shell/references/page-lifetimes.md)。

### 9.3 主题与材质

`Theme/Palette.xaml` 提供启动资源，`UiThemes.Compose` 生成运行期配色，`ThemeHost` 应用主题并在系统主题或强调色变化后重算。窗口底材与局部材质由不同层拥有；放置、回退和验证见[材质参考](../.claude/skills/momoka-winui-shell/references/materials.md)。

### 9.4 弹窗

`ContentDialog` 的外部点击由 `Theme/Styles.xaml` 中的 `EgDialogSurfaceStyle` 接到 `Views/DialogDismiss.cs`，样式接线由 `DialogChromeTests` 检查。取消行为见 [CLAUDE「弹窗」](../CLAUDE.md#弹窗)，派生样式和模板细节见 [Shell 技能「Dialogs close on outside click」](../.claude/skills/momoka-winui-shell/SKILL.md#dialogs-close-on-outside-click)。

### 9.5 能力显隐

页面和设置行根据当前能力更新显示状态，命令和服务仍各自检查权限与请求条件。规则及搜索来源栏例外见 [CLAUDE「功能可用性与显隐」](../CLAUDE.md#功能可用性与显隐)，定位实现见 [Shell 技能「Capability-dependent visibility」](../.claude/skills/momoka-winui-shell/SKILL.md#capability-dependent-visibility)。

### 9.6 动效入口

图片渐进显示从 `ImageArrivalFade` 找入口，封面到详情的关联动画由 `CardDetailTransition` 与 `ConnectedMotionReceipt` 协作。其他场景见[WinUI 动效施工文档](WinUI动效施工文档.md)和[封面关联动画](封面关联动画.md)。

媒体库动图由 `PosterLoader` 保留响应原生像素：GIF 走 WinUI，APNG 由 `AnimatedPngFrames` 后台逐帧合成、`AnimatedPoster` 按可见性与动效偏好更新画面。`AnimationSurfaceBudget` 分别限制卡片和悬浮预览的 APNG 活动画面，有限循环结束的尾帧仍持有预算直到清源；`PosterCache` 对解码位图按像素字节缓存。`CardItem` 在已有动图封面时不以静态宽图替换悬浮主图，`CardPreview` 复用播放器并给徽标接同一路径，过渡层保留首帧直到交给主图。界面尺寸仍由原布局决定。
