## 2. 实测结果

计时起点是全局只读鼠标钩子观察到 mouse-up、且当时前台 HWND 为目标窗口的时刻；终点是录屏中首次可辨识的页面离场／导航转场画面。这是外部输入到屏幕反馈的端到端延迟，包含可能的输入排队，不是应用内部 Click 方法耗时。忽略点击引起的卡片变暗、悬停按钮、首页轮播进度和自动换图，不能把这些小变化算成导航开始。

表中括号表示“上一采样仍无页面转场、下一采样首次观察到转场”的时间窗口，单位毫秒。它是采样边界，**不是严格统计置信区间，也不是精确到毫秒的内部事件时间**。

本次有三点可确定：

1. 用户描述的“先卡一下再播放页面动画”已在安全的卡片标题导航上复现，且主页、详情、媒体库多个方向都有。
2. 重复打开同一单集仍有 0.63 秒、1.39 秒左右的样本，不能宣称已有缓存解决了首帧响应。
3. 初次单集详情在约 0.64 秒的样本中已能读到标题与正文；约 0.82 秒的样本出现封面／徽标；约 1.31 秒的样本主要区域看起来稳定。这里描述的是屏幕外观，不能替代全部请求完成、播放目标可用或后台图片完成时间。

鼠标 down/up 间隔约 1–2 ms，短于 90 ms 按压动画；当前帧采样不足以可靠分离“第一次按压缩放帧”。因此本次证明的是**打开页面的反馈迟到**，没有证明按压缩放本身每次迟到。后续必须另测按住再松开的 PointerPressed 反馈。

录屏工具请求 30 帧／秒，实际只有 23.14–27.47 帧／秒，存在 38–59 ms 的转场边界采样间隔。**这是采集速率，不是 Momoka FPS。** 录制和图片编码会增加本机负载；这些结果是带采集负载的基线，不宜据此计算性能提升百分比或 p95。

## 3. 源码确认与疑点

### 3.1 点击与同步导航：首帧前的重点审查对象

[主页点击](../src/Momoka.Shell/Views/HomePage.xaml.cs) 1470–1473 行直接进入打开条目；[Shell 导航](../src/Momoka.Shell/Views/ShellPage.xaml.cs) 1381–1393、1447–1457 行在同一次输入调用中同步调用 `Frame.Navigate`。普通浏览选择 `EntranceNavigationTransitionInfo`（1835–1837 行）。

[DetailPage](../src/Momoka.Shell/Views/DetailPage.xaml.cs) 78–86 行构造 VM、执行 `InitializeComponent` 和初始绘制；1686–1739 行同步解析依赖、Attach、更新标题／遮罩／集数区域，再调用 `ReloadAsync`。[DetailViewModel](../src/Momoka.Shell/ViewModels/DetailViewModel.cs) 2254–2303 行 Attach 重建五个货架并通知绑定；2312–2327 行首次 await 前仍执行 BeginLoad 和 Preview。fire-and-forget 不会使首次 await 前的工作自动进入后台线程。

Preview 的 `AnnounceShape` 在 2474–2555 行直接发布 44 个派生属性通知，并调用额外的能力通知；详情 GET 后 Apply 再走一次同类通知。这里可能集中触发布局、可见性和重画工作，**尚无采样栈证明其耗时占比**。XAML 行数不能代替控件数量或初始化时间。

### 3.2 页面转场阶段不能误认成业务阻塞

旧页面仍在屏幕上，有可能包含平台退出动画、等待布局和呈现调度，不等于 UI 线程持续阻塞。[主页](../src/Momoka.Shell/Views/HomePage.xaml.cs) 1412–1428、1461–1467 行离页时立即取消动画和 VM；[折叠逻辑](../src/Momoka.Shell/Views/HomePage.xaml.cs) 495–527 行的定时器只调度后续重判，没有在导航链等待其动画结束。

本轮进一步核对了实际发布的 `Microsoft.UI.Xaml.dll`：它与本机 WinUI 2.3.9 包中的 DLL 哈希相同（`AAD12524765E6FB63F0AE26A45A9BA3104F24FDE66413D8A3036FBED74A1E990`），FileVersion 为 `3.2.0.2511`，版本资源带源码提交 `693f472aeaf89c6dff66256ee6fcd453e5d553b8`。该提交的 [ThemeTransitions.cpp](https://github.com/microsoft/microsoft-ui-xaml/blob/693f472aeaf89c6dff66256ee6fcd453e5d553b8/dxaml/phone/lib/ThemeTransitions.cpp#L3185) 3185–3206 行定义：前进时旧页从动画 0–150 ms 淡出，新页前 150 ms 透明并保持偏移，150–450 ms 上浮。**150 ms 是转场开始后的退出时间，不能解释点击后旧页静止 425–1392 ms 才开始离场。** 该提交的 [Frame_Partial.cpp](https://github.com/microsoft/microsoft-ui-xaml/blob/693f472aeaf89c6dff66256ee6fcd453e5d553b8/dxaml/xcp/dxaml/lib/Frame_Partial.cpp#L407) 407–415、492–497、645–660 行同步取新页面、设置 Content 和调用导航钩子，没有先 await 旧页退出完成。这里仍不能区分输入排队、页面创建／清理、布局与 GPU 呈现各占多少时间。

现有代码没有“封面飞到详情”的 ConnectedAnimation 或导航截图搬运路径。主页货架的 440 ms 入场与错峰、折叠动画、详情 Showcase 尺寸动画是不同场景，不能用它们的时长解释所有点击前的停顿。

必须把“点击→导航开始”“旧页退出→新页出现”“新页→主要内容完成”分开取证，才能判断该减同步工作还是调整转场。不能凭视频总时长直接删动画。

### 3.3 已有 seed 首屏与异步图片，不应重复设计

[DetailViewModel](../src/Momoka.Shell/ViewModels/DetailViewModel.cs) 2320–2327、2409–2447 行在主体 GET 前 Preview 现有卡片资料并开始图片读取；非 stub 可以先给出标题、简介和状态。图片并发读取，不是 `EndLoad` 必须等待的所有依赖。图片标签相同会保留已有图片（2658–2661 行）。

[PosterCard](../src/Momoka.Shell/Views/PosterCard.xaml.cs) 533–544 行收到 PointerPressed 后同步启动按压反馈，429 行 Begin；没有先 await 网络。读取这些代码不能证明第一帧已经呈现。

### 3.4 “能看”与“能操作”被同一个 Busy 绑在一起

[DetailViewModel](../src/Momoka.Shell/ViewModels/DetailViewModel.cs) 2210–2215 行的 `CanPlay` 要求 `!Busy` 且目标存在；2337、2367–2369 行 Similar 与主体链并行，但必须等它结束才清 Busy。剧页还有季→集→目标轨道／信息的依赖链（2954–2980、3055–3134 行）。

因此，推荐请求很慢时，即使播放目标已经完整就绪，按钮也可能仍不可用。这是**代码确定的可操作延迟耦合**，不是已实测的页面动画根因。本轮没有点击播放按钮或单独测接口耗时。

### 3.5 重复访问仍有对象重建和图片处理

[HomePage](../src/Momoka.Shell/Views/HomePage.xaml.cs) 1400–1408 行已有快照优先、后台核对；[HomeViewModel](../src/Momoka.Shell/ViewModels/HomeViewModel.cs) 471–497 行恢复时仍重建卡片和轮播对象。[LibraryViewModel](../src/Momoka.Shell/ViewModels/LibraryViewModel.cs) 1592–1600 行暖返回清空并重造卡片；[LibraryPage](../src/Momoka.Shell/Views/LibraryPage.xaml.cs) 714–718 行恢复滚动会强制 UpdateLayout。

详情图片读取与列表的解码对象缓存不同：[CardItem](../src/Momoka.Shell/Views/CardItem.cs) 784–786 行可以命中解码缓存；[DetailViewModel](../src/Momoka.Shell/ViewModels/DetailViewModel.cs) 3504–3506、3526–3528 行仍从字节进入解码。暖访问可能免下载但不免图片处理，尚未记录实际命中率。

[HeroPictureLoader](../src/Momoka.Shell/Media/HeroPictureLoader.cs) 59–61 行复制像素，74–75 行再分配和复制；BoxBlur 才明确 Task.Run（76 行），后续仍有 BMP 编码及 BitmapImage 交接（81–93 行）。半径零也经过这条交接。部分复制／发布回到调用上下文；不能声称所有系统解码运算都在 UI 线程。它是动画中后段卡顿和暖访问成本的候选。

### 3.6 长剧和深返回需独立处理

[EmbyClient](../src/Momoka.Core/Emby/EmbyClient.cs) 477–488 行集数请求不传 Limit；[DetailViewModel](../src/Momoka.Shell/ViewModels/DetailViewModel.cs) 3052–3109 行可读取全剧、排序并集中 Fill 主集／特别篇。集合 Clear／逐项 Add 与派生属性通知会随总集数增长，虚拟化不能消除所有 VM 发布成本；不能因此声称全部图片同时解码。

[BrowseSnapshotStore](../src/Momoka.Core/Emby/BrowseSnapshotStore.cs) 65–69 行快照最多 400 项、Home 3 个、Library 6 个、有效期 10 分钟。搜索、收藏、推荐、即将播出不是普通网格快照路径（LibraryViewModel 1340–1341 行）。快照不覆盖原 LoadedCount 时，[LibraryPage](../src/Momoka.Shell/Views/LibraryPage.xaml.cs) 570–594 行仍需串行补读原深度。本轮电影库仅 43 项，未验证长剧或超过 400 项深返回。

## 4. 推荐优化路线

先走 A，再根据采样决定 B 的范围。以下是审查建议，尚未实施，也未得到实测提速值。

| 路线 | 做法 | 收益与代价 | 建议 |
| --- | --- | --- | --- |
| A：收缩首屏同步工作、分阶段加载 | 合并重复通知；只初始化／发布当前首屏必需数据；附属区域后补；已有 seed 路径继续使用 | 直接针对多个页面的迟到；需维护各区域状态及取消守卫 | 首选 |
| B：有限缓存与稳定集合 | 复用合适尺寸的图片；快照按变化更新卡片；滚动锚点恢复；局部延后不在首屏的控件创建 | 改善重复访问；增加生命周期、内存预算和失效逻辑 | 采样后定范围 |
| C：仅缩短转场或给整页加缓存 | 改平台转场、NavigationCacheMode，或无条件预加载详情 | 可能减少感知等待；不能保证消除同步成本，可能保留旧账号状态、持有大树或增加网络负载 | 不作为首轮方案 |

### P0：补齐内部阶段计时，形成可比较基线

不改业务行为的后续性能采集应标记：PointerPressed、Click、Frame.Navigate 起止、页面构造／InitializeComponent、Attach／Preview、首次布局与 Rendering、主体 GET／附属 GET、Apply／集合发布、图片命中／解码／赋值。标记只包含阶段名、匿名运行 ID、耗时和数量，不包含令牌、服务器地址或带凭据 URL。

同一次场景用 WinUI／CPU 采样区分：UI 执行时间、等待网络、框架转场和呈现延迟。CPU 栈、XAML 事件和逐帧画面互相印证。优先验证从点击到第一转场的 0.4–1.4 秒，而不是先优化下载吞吐。

重复测同一入口至少 20 次，并保留首访、重复访问和无录屏对照；记录当前发布哈希、窗口尺寸、图片命中和后台负载。实机环境保持一致，统计中位数／p95，失败与超时单列。本轮九次样本不能充当 p95。

### P1：让反馈和轻量首屏先得到呈现机会

收缩 Navigate 前后的同步创建、重复 Paint 与派生通知；Preview／Apply 比较实际变化再通知，集合批量发布避免每次 Add 都重算整个页面版式。先保证首屏标题、已有封面和基础版式可读，再补非首屏货架、角图和页尾图。

把主体状态、播放目标状态和 Similar／季卡／图片等附属状态分开。主体目标验证完成后恢复适用操作，推荐失败只在对应区域反馈并允许恢复。保留来源、账号、条目、请求代际、版本／轨道及离页取消检查；加载和失败需要明确反馈，不能用隐藏掩盖错误。

不要只加入 Task.Yield／固定 Delay 就声称反馈已呈现；后台化仅用于可脱离 UI 的计算，不能在后台创建或操作必须依附 UI 的对象。若首屏初始化仍昂贵，再选择局部延迟创建；按名字访问和 Storyboard 目标必须先审查，不能机械给现有树添加 x:Load。

### P2：减少重复访问的图像与布局成本

优先复用详情封面和首屏背景，缓存键必须包括来源、条目、图片类型／标签、解码宽度；背景渲染还包括模糊半径。容量按实际字节控制，账号退出／图片标签变化及时失效。已有不同尺寸缓存只能作为预览候选，不能当成最终图。

把像素副本、可移走的编码／计算放在合适后台边界，UI 只做必要的图像对象交接和赋值。评估无模糊时是否可以跳过完整像素重编码，先验证色彩、方向、裁切和解码预算。首屏图优先，页尾与不可见装饰延后。

Home／Library 复用稳定集合和未变卡片，恢复滚动尽量避免连续强制 UpdateLayout。先测命中后的对象构建／布局，再决定缓存量；不要仅增加 400 项上限。

### P3：长剧与深页按需工作

长剧先准备当前季／当前集附近的可见集合，纯排序和 DTO 整理在安全边界后台完成；UI 发布采用有预算的批次。全剧业务索引可与当前显示窗口分开，分页不得破坏最早未看集、全剧顺序、特别篇和同窗换集语义。

深返回考虑恢复滚动锚点及附近窗口，再按需补读，避免“从第一页重放所有历史页”。Emby、Jellyfin、飞牛与 Plex 的媒体库各有独立路径，不能只测 Emby 就称全部服务器优化完成。MoviePilot／AniBT 本次没有深审。

## 5. 后续验收建议

下面的数值是建议目标，不是本次测得结果，也不是平台保证。

| 指标 | 建议验收目标 |
| --- | --- |
| PointerPressed→首个可见按压反馈 | p95 ≤ 100 ms；另用较长按住时间测，避免短点击漏采 |
| Click→首个真实页面转场／轻量加载反馈 | p95 ≤ 150 ms；必要时拆分平台固定阶段后再定最终预算 |
| 普通重复访问→首屏可读 | p95 ≤ 300 ms；不等待 Similar 和页尾装饰 |
| 一次连续 UI 工作 | 尽量 ≤ 16.7 ms；50 ms 以上任务逐项分析并消除不必要工作 |
| 推荐请求故意延迟 | 主体就绪和适用操作不受它拖延；区域错误／恢复可用 |

用本地 `dotnet-trace` 的 managed sample profiler 采了 20 秒，期间跑 3 次详情导航。Top exclusive 以等待为主：`LowLevelLifoSemaphore.WaitForSignal` 42.09%、`WaitHandle.WaitOneNoCheck` 17.52%、`IOCompletionPoller.Poll` 8.76%；UI 线程堆栈里出现的应用/XAML 帧主要是 `PosterCard..ctor`／`InitializeComponent`、`FrameworkElement.MeasureOverride`、`Application.LoadComponent` 和 `Frame.Navigate`，没有某个 managed 方法独占大头。

### 7.5 结论与对 P1 的输入

1. Click→`Frame.Navigate` 只有约 0.3 ms，应用内 PointerPressed→Click 也只有 6–15 ms；**点击路由不是迟到主因**。
2. 重复详情在约 53 ms 内完成 `Navigate`，首渲染中位数约 249 ms；录屏样本的可见转场在 664–698 ms。**内部导航完成与用户看见转场之间仍有约 160 ms 以上的差距，落在平台转场／原生布局呈现一侧，尚未归因到具体函数。**
3. 首次详情比重复慢约一倍（`Loaded` 521 对 227、首渲染 534 对 249）；首次创建和缓存仍值得优化，不能只看暖访问。
4. 媒体库重复在 `Attach` 结束后到首布局之间还有约 234 ms（`Attach` 结束约 50 ms，首布局中位数 286 ms）；卡片墙／首轮布局是 P1 的直接候选。
5. 主页返回的构造和 `Attach` 很快（约 10 ms），但首布局、`Loaded` 和首渲染仍为 200–500 ms；快照命中不替代卡片重建和布局。
6. 详情剧集／附属分支中位数 131 ms、图片读取结束 455 ms，都在首屏标题之后，属于“页面可读后仍继续工作”的成本；P1 要把主体状态与附属状态拆开，P3 再处理长剧。
7. 本轮 p95 受 UI 自动化检查和系统负载影响明显，不能当产品 SLA；P1 验收仍按第 5 节建议目标，但需在相同机器上用同一开关和更稳定的自动输入复测。
