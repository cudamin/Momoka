# 媒体库切换与返回主页的只读性能调查

测试日期：2026-11-03。使用当前 0.2.4 发布件及已保存账号，只读访问真实媒体服务器，未启动播放、未调用观看记录或媒体管理写入。没有修改产品源码。

## 结论

当前可连通的 Emby 与飞牛的列表请求较快，主要短板在客户端导航后重新建页面、回填控件、布局和图像处理。聚合模式也复现了请求较早完成而页面稍后才结束加载的问题。关闭动画没有稳定消除延迟，不能把动画认作唯一根因。

## 实际服务器请求

测量程序引用发布版 Momoka.Core.dll，通过正式客户端方法读取列表；耗时包含网络、正文读取、JSON 解析和适配映射，不含 WinUI 页面。每种服务器三个媒体库，各采样三轮。服务器地址、用户名、令牌和条目身份均未写入统计。

| 测量 | Emby 4.10.1.0 | 飞牛 0.9.8 |
| --- | ---: | ---: |
| 普通媒体库列表，9 次 | 6.1～42.3 ms，平均 17.3 ms | 17.7～54.5 ms，平均 31.6 ms |
| 主页轮播列表，3 次 | 13.3～23.0 ms | 23.2～40.6 ms |
| 轮播补宽图 | 约 0 ms | 27.6～40.1 ms |
| 三张海报的首次 HTTP 请求 | 97.9～128.6 ms | 159.2～245.3 ms |
| 同样海报再次 HTTP 请求 | 2.4～4.7 ms | 1.1～1.5 ms |

HTTP 的第二次请求代表连接或服务器缓存已热，不代表 Momoka 的磁盘或解码缓存。已有两张轮播背景在磁盘缓存中，读取约 7 ms；采样背景的 WIC 解码、扩边与 BMP 内存编码约 12～23 ms，未包括 BitmapImage.SetSourceAsync 和上屏绘制。

首次测量时 Jellyfin 的保存入口连接失败，匿名身份请求约 2.06 秒后抛出 EmbyUnreachableException，未传递令牌。用户随后告知连接恢复，已补测 Jellyfin 10.10.7 及三个来源聚合，见下方补测结果。没有可测的 Plex 保存账号。

原始统计：readonly-timings.json。生产 settings.json 与 settings.backup.json 在该程序前后的哈希一致。

## 真实发布页面

使用发布目录的完整副本，调用正式 Program.Run 但指定私有数据目录。保存账号、偏好和图片缓存使用副本，自动更新、MoviePilot 与 AniBT 在副本中关闭。通过正式 ShellPage.GoTo 路径导航，不点击媒体海报。各次进程结束时正常关闭自己的测试窗口。

早期单来源测试的独立构造读数：HomePage 重复创建约 6～8 ms；LibraryPage 首次创建约 241 ms，重复创建约 70～95 ms。这些读数来自早期 helper 版本，只说明页面同步创建成本，不能与后来的 HTTP/事件采样字段混用。

聚合测试连接 Emby、飞牛共两个来源、六个媒体库，两轮各返回主页九次。第二轮加入正式 VM 的 PropertyChanged 时间点，减少 UI 轮询滞后带来的误差。

| 第二轮聚合返回主页，9 次 | 最小 | 中位 | 最大 |
| --- | ---: | ---: | ---: |
| 内容清单发布（Slides 通知） | 77 ms | 124 ms | 305 ms |
| 结束加载的状态通知 | 296 ms | 414 ms | 1361 ms |
| 第一次轮播图 Picture 通知 | 454 ms | 706 ms | 2278 ms |
| 最后一项列表类响应头返回 | 76 ms | 122 ms | 305 ms |

第一轮也出现波动：返回主页最高约 2.45 秒才结束加载，约 2.78 秒观察到背景图片。第二轮连续导航的进程工作集从约 340 MB 增至 891 MB，受管内存从约 38 MB 增至 104 MB，并发生多次第 2 代 GC。它表明连续导航存在分配与回收压力；这不是泄漏证明，尚未做长时间稳定态或引用路径分析。

响应头返回不包含正文读取与解析；Picture 通知和画刷赋值不是合成器首帧，库页图片轮询又在 Ready 后才开始，因此库页图片读数不能当真实首张可见图片时间。动画开启/关闭/再开启按顺序采样，存在缓存、内存和顺序差异，不能据此断言关闭动画反而更慢。

第二轮私有 UI 测试前后生产主设置与备份哈希都一致。早期 UI 测试中生产文件哈希曾变化，不能声称全部测试期间生产文件未变；测试日志与设置服务均指向独立目录，未发现本 helper 向生产路径保存的调用。没有覆盖或恢复生产文件。

统计：ui-timings-Aggregate.json 为第二轮，ui-timings-Aggregate-first.json 为第一轮；ui-timings-Emby.json、ui-timings-FnNas.json 是早期单来源测试。

## 定位到的客户端短板

1. ShellPage.GoTo 与普通返回走 Frame.Navigate/GoBack，HomePage 和 LibraryPage 未启用导航缓存。主页进入后无条件 Attach、ReloadAsync；库页同样重新读首批。返回深滚库页时只恢复条目数与滚动位置，先重读首批，再逐页串行补读。
2. LibraryPage 每次 InitializeComponent 创建普通库暂时看不到的 MoviePilot/AniBT 搜索及资源浏览器、设置和筛选面板。Attach 的属性通知还触发 ApplyView/BuildBrowseSections，导航尾部再执行一次。独立构造实测足以证明页面有明显同步成本，尚未分别量出每个隐藏控件的份额。
3. HomeViewModel 等全部内容请求完成后一起发布。Slides 发布触发 HomeBanner.Show/SlideChanged，再同步调用 HomePage.UpdateLibraryOverlay。这段工作发生在 EndLoad 之前；UpdateLibraryOverlay、测量货架、ApplyLibraryChrome 有多处强制 UpdateLayout 和 GetOrCreateElement，是清单已到但 Ready 延后的具体排查点。
4. 普通库页每次 Attach 也调用 LoadRecentSearches，创建并请求仅空搜索页会显示的历史海报，可能与实际可见图片共用下载队列。实际争用份额尚未单独测量。
5. 普通海报有字节和解码缓存；主页轮播背景只有字节缓存，重建 BannerSlide 后重新解码、采色扩边、内存编码和 BitmapImage 交接。货架、图片与文本的进场动画进一步影响用户感觉，但不能解释所有 Ready 延迟。

具体修复顺序、状态保护和验收方式见下方「建议修复方案」。

## Jellyfin 恢复连接后的补测

仍使用同一 0.2.4 发布件和只读正式接口。Jellyfin 10.10.7 三个媒体库，各测三轮：列表请求 4.5～25.2 ms、平均 17.8 ms；主页轮播列表 15.6～22.4 ms；接下来看 76.8～87.6 ms，是该服务器内容请求中相对较慢的一项，但不足以解释约一秒的显示等待。两张 640 宽度请求的海报响应为 1,089,341 与 1,193,103 字节，私有缓存文件签名确认为 PNG；本轮 HTTP 约 11～14 ms，暖 WIC 解码约 9 ms。图片体积是优化线索，不能直接当作主要瓶颈。

Jellyfin 独立页面测试九次返回主页：内容清单发布中位 155 ms，结束加载通知中位 615 ms，第一次轮播图通知中位 815 ms，最慢 3199 ms。本轮生产主设置及备份前后哈希一致。

加入 Jellyfin 后，三个来源（Emby、Jellyfin、飞牛）、九个媒体库的聚合模式九次返回主页：

| 阶段 | 最小 | 中位 | 最大 |
| --- | ---: | ---: | ---: |
| 内容清单发布 | 158 ms | 208 ms | 371 ms |
| 结束加载通知 | 483 ms | 730 ms | 2483 ms |
| 第一次轮播图通知 | 792 ms | 1368 ms | 2646 ms |
| 最后列表类响应头 | 157 ms | 206 ms | 362 ms |

三个来源时仍有明显的内容已发布到显示阶段的间隔。相较两个来源，卡片、货架、飞牛补详情、图片任务和布局更多；测试顺序、缓存和内存状态也不同，不能将差值全部归给 Jellyfin 或单个请求。

本轮产品源码未修改，未启动播放或执行服务器写入。程序使用独立设置和缓存副本；三个来源测试前后生产主设置哈希一致，但备份哈希发生变化，结束后同时观察到另一个来自正式目录的 Momoka 进程。因此不能声称整个时间段生产备份未变；未覆盖或恢复该文件，也未关闭用户进程。

新增统计：readonly-timings-Jellyfin.json、ui-timings-Jellyfin.json、ui-timings-Aggregate3.json。库页图片计时仍受 Ready 后轮询限制；轮播通知是图片赋值而非精确上屏帧。

## 建议修复方案

状态：方案建议，尚未实施。推荐先减少重复界面工作，再复用已加载内容，最后优化轮播图片。服务器列表请求已较快，单纯缩短动画或压缩 PNG 不能解决目前的主要等待。

### 第一轮：减少重复布局和无关初始化

- 主页的页面尺寸、轮播尺寸、幻灯片变化统一排队合并处理，增加重入保护；位置、尺寸和宿主内容没有变化时跳过重复写入与布局。先统计各步骤次数和耗时，再减少强制 UpdateLayout；保留媒体库升降动画所需的前后几何读取、窗口变化响应和正确终点，不能直接删除全部强制布局。
- 媒体库 Attach 期间合并视图与分区变化，依赖附加完成后只执行一次最终 ApplyView、BuildBrowseSections 和头部布局，避免属性通知与导航尾部重复更新。
- 搜索历史图片仅在实际展示历史的空搜索页加载，普通媒体库不请求这些隐藏图片；搜索、来源切换和重新进入时按需求恢复。
- MoviePilot、AniBT 搜索面板及设置、筛选面板通过统一入口在首次使用时创建。先调整 constructor、Attach、Release 和绑定的访问边界，释放路径兼容尚未创建的面板；不能只加 x:Load=False，造成命名控件空引用或动画目标缺失。搜索页四个来源入口及不可用说明继续遵守现行规则。

这一轮范围较小，优先验证界面工作次数是否减少。预期减少换库的同步阻塞与主页内容发布后的布局等待，收益需实测，不先承诺加速比例。

### 第二轮：有限复用主页和最近媒体库内容

- 同一有效身份和查询下，返回时先显示已有条目、封面及滚动位置，后台检查更新；有变化再局部增删和更新，保持绑定集合稳定。缓存命中后不先从第一页串行重读此前浏览的全部分页。
- 优先保存有上限的条目快照与滚动状态，复用现有图片缓存；评估后再决定是否保留独立页面实例。主页及最近媒体库的缓存设条目数量与内存预算，按最近使用淘汰。页面离开时取消无用请求、暂停计时器和实时订阅，淘汰时释放引用，避免无限保留页面、旧来源或整批位图。
- 缓存按账号及有效登录代次、在线来源集合、库、分区、排序、筛选、搜索条件、显示字段及「将项目分组到合集中」等影响实际查询的显示选项区分。账号退出、来源增删、查询改变、删除或修改媒体、缓存过期及显式刷新时，失效或更新对应内容；后台结果继续检查取消、加载代次及来源身份，旧结果不能覆盖新页面。
- 手动刷新保留强制重新读取的语义。后台刷新失败时可保留有效缓存并显示失败和重试入口；账号或权限失效时不能继续展示已无权读取的内容。

不直接把所有 LibraryPage 改成 NavigationCacheMode.Required/Enabled：Frame 按页面类型缓存，不能区分不同 LibraryRequest；同一类型还承载搜索、收藏和文件夹等请求。当前 Attach 也仍会重读，单加缓存开关不会自动解决等待，且容易残留其他库的筛选、来源和卡片状态。

这一轮对「返回还要重新等一遍」的改善最直接，代价是增加缓存失效与生命周期管理；预算和淘汰策略必须与性能一起验证。

### 后续：轮播图片与聚合逐排显示

- 复用已经解码、扩边和编码的轮播背景，避免每次返回都重新处理。缓存键包含来源身份、图片身份和 tag、请求及解码尺寸、处理规则，并设内存上限；图片更新或来源失效后不能沿用旧图。
- 聚合主页各排内容独立回填，快来源先出现，慢来源保留自己的加载、错误和重试状态。继续观看等跨来源行沿用正确的合并、顺序与去重语义，迟到结果仍受页面和来源有效性保护。
- 动画时长和 Jellyfin PNG 格式作为后续独立评估项；先测实际可见图片、布局和解码阶段，再决定是否调整，不以关动画或改质量替代前两轮修复。

### 验收目标与回归检查

以当前三来源、九个媒体库为比较基线，保持窗口尺寸、来源、数据与缓存温度可比；首次进入、立即返回、深滚后返回分别测量。交错运行有动画和无动画场景，报告中位数、高分位及最慢值，不用单个最快样本作为结论。

| 检查 | 目标或判据 |
| --- | --- |
| 第一轮工作量 | 普通库页隐藏历史图片请求为 0；尚未使用的无关面板构造为 0；一次 Attach 只执行一次最终视图和分区更新 |
| 暖缓存返回 | 200 毫秒内出现可用内容作为拟验收目标，尚未达成；同时核对滚动位置、可见卡片和可用操作，不能只看 Ready |
| 主页阶段计时 | 分别记录内容任务完成、卡片及行集合发布、布局、图片解码与赋值、首张可见图片；通知与赋值仍不能冒充精确上屏帧 |
| 来源和查询隔离 | A→B→A、换账号、增删来源、改筛选或排序均不串数据；旧请求不能回填新访问 |
| 更新与失败 | 手动刷新、入库变化、删除、后台失败与重试均保持正确反馈；刷新无需拆掉未变化的行 |
| 连续导航与释放 | 反复切换并观察较长稳定态，内存受预算约束、淘汰后可回收，离页计时器和订阅停止；不能仅凭单次工作集上涨判定泄漏 |
| 现有界面行为 | 媒体库升降、轮播避让、返回滚动、宽窄窗口、搜索来源和面板首次打开／重开保持正确 |

实施时补充取消、代次、缓存失效和淘汰的自动测试，并按 CLAUDE.md 对最终代码完成适用编译、测试与真实页面验证；各服务器库页分别核对，聚合模式另测。本方案文档的完成不代表产品修复完成或上述速度目标已经达成。
